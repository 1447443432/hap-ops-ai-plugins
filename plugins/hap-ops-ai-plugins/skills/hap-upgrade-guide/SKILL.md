# HAP 私有部署升级指南

本 skill 只依据实时官方页面生成升级结论和文档。用户提供的 WorkBuddy 文档只作为章节、详细程度和排版参考，不作为版本事实、命令或下载地址来源。

## 必须读取的资源

生成文档前必须读取：

1. 单机：`assets/upgrade-guide-template-standalone.md`
2. 集群：`assets/upgrade-guide-template-cluster.md`
3. `references/upgrade-rules.md`
4. `references/merge-rules.md`
5. `references/site-structure.md`、`references/command-library.md`

只读取与当前模式和任务有关的部分；但模板和 `upgrade-rules.md` 必须完整遵守。

## 触发与信息收集

以下任一事项必须触发本 skill：HAP 私有部署升级、跨版本升级、升级注意事项、升级前后附加操作、单机/集群升级、AMD64/ARM64 镜像支持、升级文档或升级方案审核。

生成文档前收集且确认以下 5 项：

1. 当前版本
2. 目标版本
3. 部署模式：单机或集群
4. 服务器架构：AMD64 或 ARM64
5. 网络：可访问互联网或离线

信息缺失时，使用客户端支持的结构化单选控件；普通文本对话不假设存在弹窗按钮。信息全部收集完成后，统一展示一次升级参数摘要，再开始网页抓取，不等待用户回复“确认”。

## 实时核验顺序

1. 抓取 `https://docs-pd.mingdao.com/version`，核验当前版本、目标版本发布日期、架构支持和跨版本路径。
2. 按低版本到高版本逐个抓取 `https://docs-pd.mingdao.com/upgrade/{版本号}/`，不得只抓带标记的版本。
3. 完整读取每个版本的“升级说明”、注意框、折叠区域、配置、代码、列表、表格和参考链接；参考链接必须继续抓取并展开为可执行步骤。
4. 按部署模式过滤操作：单机不得出现 `kubectl`、`crictl`、`ctr`；集群不得出现 `docker exec`、`docker-compose`、`service.sh restartall`。
5. 任何页面抓取失败、页面为空或无法解析时，停止生成并报告原因，不得用记忆、旧缓存或旧产物补全。

## 生成原则

- 必须以对应模板为不可变骨架，只能填充和裁剪明确不适用的条件块。
- 不得把模板改写成“结论 + 摘要 + 少量命令”；官方步骤、警告、适用条件、执行位置、默认路径、完整命令、配置、列表和验证必须保留。
- 升级前和升级后附加操作分别按来源版本从低到高排列；同一版本按官方出现顺序排列。
- 每条附加操作标题必须包含 `来自 v{版本号}`；合并同类操作时列出全部来源版本并保持升序。
- 未明确标注“升级后/微服务升级后/HAP 升级后/重启后/升级完成后”的可执行注意事项，一律列为升级前附加操作并注明时机判断。
- 版本信息、下载地址和命令必须来自本次实时官方页面，不得直接复制 WorkBuddy 旧产物的事实内容。

## 单机硬约束

- 固定章节：`### 提前准备`、`## 升级前准备`、`## 升级步骤`、`## 升级后验证`、`## 异常情况排查`、`## 参考文档`。
- “升级前准备”严格按授权有效期、前端二次开发、数据备份、确认当前版本、检查资源排列。
- 单机数据备份只保留：
  `> ⚠️ **升级前必须完成备份，此步骤不可跳过。**`
  和完整官方 URL：`https://docs-pd.mingdao.com/deployment/docker-compose/standalone/data/backup`。
- 单机数据备份区域禁止出现 `docker exec`、`mongodump`、`backup mysql mongodb file` 或任何自定义备份命令。
- 第一阶段附加操作标题必须是 `#### N. 来自 v{版本号}：{标题}`。
- 第二阶段固定使用 `#### 1. 修改镜像版本号`、`#### 2. 重启服务`，不得降级为 h3。
- 离线 HAP 镜像导入、验证命令前必须在同一 bash 代码块写用途注释。
- 外部 S3/OSS/COS/OBS 只有在官方本次路径明确要求时才加入；需在“提前准备”提供 `preset_file` 完整裸 URL，并注明“仅外部 S3 时执行”。

## 集群硬约束

- 固定章节：`## 提前准备`、`## 升级前准备`、`## 升级步骤`、`## 升级后验证`、`## 参考文档`。
- “升级前准备”严格按授权有效期、前端二次开发、数据备份、确认当前版本、检查资源排列。
- 第一阶段的镜像改名、MongoDB 建库、`service.yaml`、MongoDB 预置数据等标题均需标注来源版本。
- `service.yaml` 删除、已有 Service 修改、新增 Service 必须拆分为独立步骤；完整保留官方 YAML 字段、版本、执行顺序和缩进说明。
- 第二阶段固定包含 `#### 1. 滚动更新` 和 `#### 2. 非滚动更新`；保留内存前置条件、停止/更新/状态验证命令。
- 第三阶段进入 config Pod 的步骤可作为固定入口；其余附加操作逐版本按升序标注 `来自 v{版本号}`。
- fileInit 必须分别保留内置存储、S3/对象存储和外部对象存储的适用条件及官方命令；集群外部对象存储预置包必须提供完整裸 URL。
- 离线镜像使用 `gunzip -c xxx.tar.gz | ctr -n k8s.io image import -`，不得拆成解压后再导入；导入和 `crictl images` 验证前必须有用途注释。

## Markdown 与 HTML 交付闸门

Markdown 必须使用真实 ASCII 反引号和成对代码围栏；下载表格中的 URL 必须是裸 `https://` 地址，禁止 Markdown 超链接或反引号包裹。版本信息表格必须位于标题之后，普通说明不得使用一级标题。

写入 Markdown 后必须执行：

```bash
python tools/finalize_upgrade_doc.py {markdown文件} {html文件} --mode single
```

集群将 `--mode single` 改为 `--mode cluster`。禁止直接调用 md2html。`finalize_upgrade_doc.py` 会先运行 `validate_upgrade_doc.py`；校验失败时禁止生成或交付 HTML。

最终回复必须报告 Markdown 校验和 HTML 生成结果。没有实际的校验通过结果，不得声称文档完成。

## 质量检查

- 逐版本附加操作完整采集且顺序为低到高。
- 所有附加操作标题含来源版本。
- 单机无集群命令，集群无单机命令。
- 单机备份仅含强制提示和官方链接。
- 外部对象存储仅在官方明确要求时出现，且有对应裸下载 URL。
- 集群 `service.yaml`、fileInit、滚动/非滚动更新没有摘要化。
- 下载表格、代码围栏、标题层级、重复正文和 HTML 均通过工具校验。
