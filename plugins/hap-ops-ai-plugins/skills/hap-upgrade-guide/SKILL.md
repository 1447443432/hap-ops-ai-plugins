# HAP 私有部署升级指南

本 skill 只依据实时官方页面生成升级结论和文档。用户提供的 WorkBuddy 文档只作为章节、详细程度和排版参考，不作为版本事实、命令或下载地址来源。

如果当前环境同时存在其他 HAP 升级 skill，生成 Markdown/HTML 时必须优先使用本 `hap-upgrade-guide` skill；其他 skill 的“结论与路径/离线资源/升级前检查/验证与回退”摘要骨架不得替代本 skill 模板。

## 必须读取的资源

生成文档前必须读取：

1. 单机：`assets/upgrade-guide-template-standalone.md`
2. 集群：`assets/upgrade-guide-template-cluster.md`
3. `references/upgrade-rules.md`
4. `references/merge-rules.md`
5. `references/site-structure.md`、`references/command-library.md`

只读取与当前模式和任务有关的部分；但模板和 `upgrade-rules.md` 必须完整遵守。

## 触发与信息收集

以下任一事项必须触发本 skill：HAP 私有部署升级、跨版本升级、升级注意事项、升级前后附加操作、单机/集群升级、AMD64/ARM64 镜像支持、升级文档或升级方案审核。

生成文档前收集且确认以下 5 项：

1. 当前版本
2. 目标版本
3. 部署模式：单机或集群
4. 服务器架构：AMD64 或 ARM64
5. 网络：可访问互联网或离线

信息缺失时，使用客户端支持的结构化单选控件；普通文本对话不假设存在弹窗按钮。信息全部收集完成后，统一展示一次升级参数摘要，再开始网页抓取，不等待用户回复“确认”。

## 实时核验顺序

1. 先抓取 `https://docs-pd.mingdao.com/hap/version`，核验当前版本、目标版本发布日期、架构支持，并以“含附加操作”列建立跨版本清单。
2. 将路径版本分为两类：
   - **动作版本**：总表“含附加操作”列标记 `√` 的版本。必须抓取并完整读取其升级详情、注意框、折叠区域、配置、代码、列表、表格和参考链接；参考链接必须继续抓取并展开为可执行步骤。**唯一例外是集群 fileInit 的“情况 3：外部文件对象存储”**，最终文档只保留官方 OSS 文档链接，不展开厂商命令、bucket 上传或 endpoint 配置步骤。
   - **节点版本**：总表“含附加操作”列为空的中间版本。仅用于内部路径判定，不访问详情页，不增加附加操作；最终文档的版本清单只展示动作版本，不展示节点版本。目标版本若未标记附加操作，仍保留在顶部升级路径和目标版本发布日期中，但不作为附加操作展示。
3. 对动作版本，按版本号从低到高逐个抓取详情页；不得并行抓取，不得重复抓取已经成功读取的版本。
4. `/version`、动作版本详情页及其必要参考页每次访问的超时时间为 60 秒；失败、超时、页面为空或无法解析时，使用同一 URL 最多重试 3 次。第 2、3 次必须重新发起请求，不得改用猜测 URL、搜索摘要、截图或旧产物补全。
5. `/version` 或单个动作版本/必要参考页连续 3 次失败后，停止生成并报告具体版本、URL 和失败原因；不得继续抓取后续版本，也不得交付不完整文档。
6. 对节点版本，仅当版本总表本身抓取失败、架构状态无法确认，或总表标记与已获取详情出现冲突时，才停止生成并报告原因；节点版本不访问详情页。
7. 按部署模式过滤操作：单机不得出现 `kubectl`、`crictl`、`ctr`；集群不得出现 `docker exec`、`docker-compose`、`service.sh restartall`。

> **关键判定**： “逐版本核对路径”不等于“逐版本强制抓详情页”。先以 `/version` 的附加操作标记筛选动作版本，再对动作版本做深度采集；这样既不漏附加操作，也不会因无附加操作版本的详情页不可用而误阻塞。

## 关系型数据库变更 SQL 来源

当升级详情要求执行关系型数据库 DDL，或用户明确指定了 OceanBase、达梦、人大金仓等非 MySQL 数据库时，必须使用本次官方对外公开的数据库变更 SQL 页面，不得从旧文档、缓存或记忆补全 SQL：

- 官方数据库变更 SQL 页面：`https://meihua.mingdao.com/public/view/6a59bb1b3b43b911ab153690`
- 只在路径中确实存在关系型数据库 DDL 时读取该页面；无 DDL 的版本不读取。
- 选择页面中与 HAP 版本和数据库类型匹配的 SQL。OceanBase 使用 MySQL 兼容模式的 `obclient` 执行；不得把 `mysql` 命令、HAP 容器入口或 config Pod 入口套用到 OceanBase。
- 文档必须保留该官方页面的完整裸 URL；连接地址、端口、租户、用户名和密码使用现场占位符，并明确执行前替换。

## 文件预置包链接来源

- 仅当动作版本详情明确要求 `fileInit`，且离线/外部对象存储场景确实需要时，读取官方 OSS 说明页 `https://docs-pd.mingdao.com/hap/faq/oss`，跟随页面中的“预置文件包”实际链接。
- 使用官方页面实际返回的文件名和 URL；当前 v7.3.0 对应 `https://pdpublic.mingdao.com/private-deployment/source/7.3.0/file_init.tar.gz`。生成前必须验证链接可用，禁止使用历史 `preset_file` 地址或凭记忆拼接地址。

## WorkBuddy 固定文案基线

用户提供的 WorkBuddy 成品仅作为章节顺序、标题层级、操作粒度和通用文案的参考；其中的版本日期、版本标记、命令、SQL、镜像名和下载地址都必须按本次实时官方页面重新核验。以下模式化文案应按对应模式原样保留，仅替换实时变量：

- 单机准备提示：
  `> **建议在正式开始升级操作前，提前准备本次升级实际会用到的全部资源。**`
  `> 资源不限于 HAP 微服务镜像；若附加操作涉及存储组件、文档预览、预置数据、离线脚本或其他组件资源，也必须在此节一并整理。`
- 集群准备提示：
  `> **建议在正式开始升级操作前，提前在相关节点准备本次升级实际会用到的全部资源。**`
  `> 资源不限于 HAP 微服务镜像；若附加操作涉及文档预览、存储组件、预置数据、离线脚本或新增服务镜像，也必须在此节一并整理。`
- 离线资源提示：保留“请在**可访问互联网的机器上**提前下载本次升级实际需要的全部离线文件”，单机结尾为“并上传到服务器：”，集群结尾为“并上传到对应服务器：”。
- 授权有效期、前端二次开发、数据备份、第二阶段更新/重启和功能验证沿用对应 WorkBuddy 模式成品的固定表达及顺序；只替换实时日期、版本、架构、数据库名称和链接。

## 生成原则

- 必须以对应模板为不可变骨架，只能填充和裁剪明确不适用的条件块。
- 不得把模板改写成“结论 + 摘要 + 少量命令”；官方步骤、警告、适用条件、执行位置、默认路径、完整命令、配置、列表和验证必须保留。
- 用户提供 WorkBuddy 成品时，沿用其章节顺序、标题层级、操作粒度和代码块完整度；只校正官方事实、版本号、下载地址和适用条件，不得把成品压缩成摘要，也不得擅自换成另一套章节结构。
- 禁止生成“结论与路径、离线资源、升级前检查、升级前操作、升级微服务、升级后操作、验证与回退”这套摘要式章节；这些标题出现即视为生成失败。
- 升级前和升级后附加操作分别按来源版本从低到高排列；同一版本按官方出现顺序排列。
- 每条附加操作标题必须包含 `来自 v{版本号}`；合并同类操作时列出全部来源版本并保持升序。
- `第三阶段：HAP 微服务升级后操作` 只允许放置官方明确要求在微服务升级完成后执行的变更/附加操作，例如 DDL、索引、预置数据、文件初始化、配置变更或重新授权；不得放置服务状态、日志、版本号或业务功能验证。
- 第三阶段中的“进入微服务容器/进入 config Pod”仅是执行后置变更的入口，不是验证步骤；只有存在至少一个真实的版本后置变更时才能保留，若没有后置变更，必须删除整个第三阶段（包括入口步骤）。
- 所有服务状态、容器日志、登录版本和业务功能检查必须统一放在 `## 升级后验证`；不得在第三阶段重复生成。
- `功能验证`必须且只能保留以下四项，顺序固定：打开工作表创建/编辑记录、触发工作流检查执行情况、检查统计图/报表、检查附件上传/下载/预览；禁止追加代理、AI Agent、SSE、长连接或其他验证项。
- 未明确标注“升级后/微服务升级后/HAP 升级后/重启后/升级完成后”的可执行注意事项，一律列为升级前附加操作并注明时机判断。
- 版本信息、下载地址和命令必须来自本次实时官方页面，不得直接复制 WorkBuddy 旧产物的事实内容。
- 输出文件名必须严格使用 `HAP升级指南-v{当前版本}-to-v{目标版本}-{单机|集群}-{amd64|arm64}.md` 和同名 `.html`；版本号前保留 `v`，版本之间使用 `-to-`，部署模式和架构使用短横线连接，架构使用小写。禁止使用下划线、`_离线` 后缀、架构大写或 Markdown/HTML 不同名。离线状态写入文档内容，不写入文件名。
- 版本清单展示规则：顶部元数据表保留当前版本、目标版本及其发布日期；正文“含附加操作”版本清单只展示总表中标记 `√` 的动作版本，隐藏所有未标记版本，不输出“无附加操作版本”长列表。

## 单机硬约束

- 固定章节：`### 提前准备`、`## 升级前准备`、`## 升级步骤`、`## 升级后验证`、`## 异常情况排查`、`## 参考文档`。
- “升级前准备”严格按授权有效期、前端二次开发、数据备份、确认当前版本、检查资源排列。
- 单机“5. 检查资源”必须逐句、按原顺序复用 WorkBuddy 单机成品：磁盘空间；离线时的目标 HAP 镜像校验、MongoDB 预置脚本与对应版本数据包同目录检查、升级窗口确认；“建议在升级前记录以下现场信息，便于出现异常时与升级前状态对比：”及其四条清单；以及“执行操作时，所有默认路径都必须以现场实际配置为准……”的完整结尾说明。不得改写成概括性摘要。
- 单机现场基线必须记录：HAP/存储组件/{关系型数据库名称}/MongoDB 容器名称与状态、`docker-compose.yaml` 中 HAP 镜像标签/数据目录挂载/外部代理配置、系统登录地址/组织授权状态/前端二开发布状态、备份文件保存位置/文件名/完整性校验结果；`{关系型数据库名称}` 必须替换为现场实际类型（如 OceanBase），不得保留占位符。
- 单机数据备份只保留：
  `> ⚠️ **升级前必须完成备份，此步骤不可跳过。**`
  和完整官方 URL：`https://docs-pd.mingdao.com/hap/deployment/docker-compose/standalone/data/backup`。
- 单机数据备份区域禁止出现 `docker exec`、`mongodump`、`backup mysql mongodb file` 或任何自定义备份命令。
- 第一阶段附加操作标题必须是 `#### N. 来自 v{版本号}：{标题}`。
- 第二阶段固定使用 `#### 1. 修改镜像版本号`、`#### 2. 重启服务`，不得降级为 h3。
- 离线 HAP 镜像导入、验证命令前必须在同一 bash 代码块写用途注释。
- 外部 S3/OSS/COS/OBS 只有在官方本次路径明确要求时才加入；需从官方 OSS 页面跟随获取并验证 `file_init.tar.gz` 的完整裸 URL，并注明“仅外部 S3 时执行”。

## 集群硬约束

- 固定章节：`## 提前准备`、`## 升级前准备`、`## 升级步骤`、`## 升级后验证`、`## 参考文档`。
- “升级前准备”严格按授权有效期、前端二次开发、数据备份、确认当前版本、检查资源排列。
- 集群“5. 检查资源”必须且只能保留 WorkBuddy 集群结构的三项：各节点磁盘空间、控制节点 `kubectl` 可用性、滚动更新所需各微服务节点约 40% 可用内存及不满足时使用非滚动更新的说明；不得套用单机 Docker 资源检查或额外扩展为业务验证。
- 集群“1. 授权有效期检查”必须使用 WorkBuddy 集群成品的完整重要提示（“若目标版本（日期）晚于授权到期日”），不得套用单机“目标版本的发布日期”文案；“2. 前端二次开发注意事项”逐条保留完整警告、说明、三步列表和结尾，不得压缩。生成后必须通过校验器硬校验。
- 集群“3. 数据备份”必须保留强制备份提示和“MongoDB、{关系型数据库名称（如适用）}、文件存储服务及其他有状态服务”的数据范围说明；用户指定 OceanBase 时必须明确写出 OceanBase，不得出现单机备份链接或“请参考官方备份与部署文档执行备份”。
- 第一阶段的镜像改名、MongoDB 建库、`service.yaml`、MongoDB 预置数据等标题均需标注来源版本。
- `service.yaml` 删除、已有 Service 修改、新增 Service 必须拆分为独立步骤；完整保留官方 YAML 字段、版本、执行顺序和缩进说明。
- 删除服务时，必须给出该服务完整的 Deployment 和 Service 配置示例，至少保留官方原文中的 `apiVersion`、`kind`、`metadata`、`spec`、容器、端口和探针字段；不能只写“删除 xxx 服务”。
- 新增服务时，必须给出官方完整 YAML，不得缩写、使用“同上”、省略号或只给 Deployment/Service 其中一半；除非官方明确要求在指定位置修改，否则不得把完整配置改成片段。
- 如果多个版本涉及不同服务，必须按版本从低到高分别建立附加操作块；非重复服务不得合并到一个版本块。每个版本块之间保留一个空行，YAML 对象之间保留官方 `---` 分隔符，并在 YAML 注释中标明来源版本和服务名。
- 如果是修改已有 Service 的指定位置，必须单独成块，明确文件定位、字段路径、缩进要求和仅需修改的完整片段；不得与新增服务完整 YAML 混在同一个可直接粘贴代码块中。
- 任何“如果存在/若存在/如使用/按实际情况执行/同步修改”的条件操作都不能只写文字说明；必须同时给出对应的完整命令或配置片段，并明确不满足条件时跳过。例如提到 `run.sh` 同步替换镜像名，必须给出 `if [ -f ... ]; then sed ...; fi` 完整命令。
- 任何“如存在”“若有”“同步处理”“按实际文件执行”等可执行事项都必须给出对应完整命令；例如提到 `run.sh`，必须同时给出文件判断、完整 `sed` 替换命令和 `fi`，不得只写文字提示。
- 第二阶段固定包含 `#### 1. 滚动更新` 和 `#### 2. 非滚动更新`；保留内存前置条件、停止/更新/状态验证命令。
- 第三阶段仅承载升级完成后的版本变更/附加操作；进入 config Pod 只是这些变更的执行入口，存在真实后置变更时才保留。服务状态、Pod 状态、日志、版本和功能检查全部放入“升级后验证”。
- fileInit 必须分别保留内置存储、S3/对象存储和外部对象存储的适用条件；情况 1/2 保留在 config Pod 内执行的官方命令，情况 3 只保留官方 OSS 文档链接，不生成厂商命令、bucket 上传或 endpoint 配置步骤。
- 离线镜像使用 `gunzip -c xxx.tar.gz | ctr -n k8s.io image import -`，不得拆成解压后再导入；导入和 `crictl images` 验证前必须有用途注释。

## Markdown 与 HTML 交付闸门

Markdown 必须使用真实 ASCII 反引号和成对代码围栏；下载表格中的 URL 必须是裸 `https://` 地址，禁止 Markdown 超链接或反引号包裹。版本信息表格必须位于标题之后，普通说明不得使用一级标题。

写入 Markdown 后必须执行：

```bash
python tools/finalize_upgrade_doc.py {markdown文件} {html文件} --mode single
```

集群将 `--mode single` 改为 `--mode cluster`。禁止直接调用 md2html。`finalize_upgrade_doc.py` 会先运行 `validate_upgrade_doc.py`；校验失败时禁止生成或交付 HTML。

最终回复必须报告 Markdown 校验和 HTML 生成结果。没有实际的校验通过结果，不得声称文档完成。

## 质量检查

- 逐版本附加操作完整采集且顺序为低到高。
- 所有附加操作标题含来源版本。
- 单机无集群命令，集群无单机命令。
- 单机备份仅含强制提示和官方链接。
- 外部对象存储仅在官方明确要求时出现，且有对应裸下载 URL。
