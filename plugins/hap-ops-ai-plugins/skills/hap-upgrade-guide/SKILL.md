# HAP 私有部署升级帮助

用于两类任务：

- 回答 HAP 私有部署升级相关咨询
- 生成可执行的升级指南 Markdown 文档，并自动转换为 HTML 文档

## Skill 文件结构

本 Skill 的所有文件均相对于 Skill 根目录（即本 `SKILL.md` 所在目录），安装到任何 AI 客户端后均可直接使用：

```
HAP升级指南/
├── SKILL.md                              ← 本文件（Skill 主指令）
├── references/                           ← 参考资料目录
│   ├── site-structure.md                ← 官网 URL 规律、页面入口、部署文档位置
│   ├── merge-rules.md                    ← 跨版本附加操作合并规则
│   └── command-library.md               ← 联网/离线、单机/集群、AMD64/ARM64 示例命令
├── assets/                               ← 模板目录
│   ├── upgrade-guide-template-standalone.md  ← 单机模式 Markdown 模板
│   └── upgrade-guide-template-cluster.md      ← 集群模式 Markdown 模板
└── tools/                                ← 工具目录
    ├── md2html-tools.tar.gz             ← Go 版 MD→HTML 转换工具压缩包（含编译产物+依赖）
    ├── md2html/                         ← Go 版工具解压目标目录（首次触发时自动解压）
    │   ├── main.go                      ← Go 源码入口（备份，ClawHub 兼容）
    │   └── template.html                ← HTML 模板（Go/Python 两版共用，ClawHub 兼容）
    └── md2html-py/                      ← Python 跨平台版（零第三方依赖，无需编译）
        └── md2html.py                   ← 纯标准库脚本，与 Go 版字节级一致，codex/无 Go 环境首选
```

> **两版转换工具的关系**：`tools/md2html/`（Go 二进制）与 `tools/md2html-py/`（Python 脚本）共用同一份 `template.html` 与 CSS/JS 规范，输出**字节级一致**。优先用 Go 二进制（单文件、最快）；当客户端无 Go 运行时或解压失败（如 codex 环境）时，回退到 Python 脚本（仅需 `python3`（或 `python`），零依赖）；两者均不可用时再由 AI 手工转换。

**文件用途速查**：
- **生成升级文档时必须读取**：模板（`assets/`）+ 参考资料（`references/`）
- **转换 HTML 时优先使用**：`tools/md2html/md2html(.exe)`（Go 版，首次运行自动从 `md2html-tools.tar.gz` 解压）；若缺失 Go 运行时则回退到 `tools/md2html-py/md2html.py`（Python 版，零依赖，免编译）；两者均不可用时 AI 直接转换
- **Skill 指令本身**：`SKILL.md`（你正在阅读的文件，包含完整工作流和 CSS/JS 规范）

核心原则：

- 只依据官方文档和实时页面内容回答，不能凭记忆补全版本细节
- 允许跨版本直接升级，但必须合并跨越路径中的附加操作
- 架构兼容性以 `https://docs-pd.mingdao.com/version` 总表实时标记为唯一准则
- 所有命令必须保持官方原意，不擅自改写命令逻辑

## 何时使用

出现以下任一情形时，必须使用本 skill：

- 用户询问某个 HAP 私有部署版本是否能升级到另一个版本
- 用户询问升级前要做什么、会跨过哪些附加操作、是否支持跨版本升级
- 用户要求输出升级步骤、升级 SOP、升级文档、升级手册
- 用户给出当前版本、目标版本、部署模式、架构、联网情况，请求生成文档
- 用户询问某一目标版本是否支持 `AMD64` 或 `ARM64`

如果任务不是 HAP 私有部署升级，而是一般部署、故障排查、功能使用说明，不使用本 skill。

## 输出类型与产物产出严格约束

根据用户意图，在以下两种输出之间选择：

- **咨询答复**：给出结论、依据、风险点、缺失信息。仅输出文本，不生成文件。
- **升级指南**：必须产出 **Markdown + HTML 双文件**（见下方强制约束）。

如果用户明确要求"生成文档""给我一份操作手册""整理成升级指南"，按升级指南处理。否则默认先给咨询答复；当信息齐全时，也可以直接生成文档。

### ⚠️ 升级指南产物产出强制约束

> **一旦进入升级指南生成模式，以下规则不可绕过、不可省略：**

#### 一、双产物强制产出

每次生成升级指南，**必须产出两个文件**：

| 产物 | 文件名 | 产出方式 |
|------|--------|---------|
| **Markdown 文档** | `{命名}.md` | AI 按模板填充后直接写入文件 |
| **HTML 文档** | `{命名}.html` | 从 MD 转换（见下方转换规则） |

- **禁止**只生成 `.md` 不生成 `.html`
- **禁止**只生成 `.html` 不生成 `.md`（MD 是唯一事实来源，HTML 永远是派生品）
- **禁止**把 MD 内容以内联文本形式输出而不写入文件
- **禁止**跳过 HTML 生成步骤（即使用户说"先只要 md"也要提醒并补上 html）

#### 二、产物结构强制基于模板

生成 Markdown 时，**必须先读取对应模板**，再在模板基础上填充内容：

- 单机模式 → 必须先读取（如 WorkBuddy 的 Read 工具，或等效的文件读取能力） `assets/upgrade-guide-template-standalone.md`，禁止凭记忆重写
- 集群模式 → 必须先读取（如 WorkBuddy 的 Read 工具，或等效的文件读取能力） `assets/upgrade-guide-template-cluster.md`，禁止凭记忆重写

模板定义了产物**必须包含的章节和顺序**，AI 只有填充权，没有结构改动权：

| 章节 | 单机 | 集群 | 说明 |
|------|:--:|:--:|------|
| 版本信息表格 | ✅ | ✅ | 两列表格格式 |
| 提前准备 | ✅ | ✅ | 仅列实际需要的资源 |
| 升级前准备（授权→前端二开→备份） | ✅ | ✅ | 严格三项顺序 |
| 第一阶段：升级前操作 | ✅ | ✅ | 按实际重排编号 |
| 第二阶段：升级微服务 | ✅ | ✅ | 含 ENV_APP_VERSION |
| 第三阶段：升级后操作 | ✅ | ✅ | 版本从低到高 |
| 升级后验证 | ✅ | ✅ | — |
| 异常情况排查 | ✅ | ❌ | 仅单机 |
| 参考文档 | ✅ | ✅ | 动态裁剪 |
| 底部声明 | ✅ | ✅ | AI 生成声明 |

#### 三、HTML 转换规则

MD → HTML 按以下优先级（工具可用性已在 **Step 0** 中确认）：

1. **首选**：`tools/md2html/md2html(.exe)` 直接调用（Go 二进制，单文件最快）
2. **回退**：若 Go 二进制不可用但存在 `tools/md2html-py/md2html.py`，用 `python3 tools/md2html-py/md2html.py -input xxx.md -output xxx.html` 调用（若环境中命令为 `python` 而非 `python3`，则改用 `python`；零依赖，跨平台等价）
3. **兜底**：两者均不可用时，AI 按 SKILL.md 中的 CSS/JS 规范手工转换

无论哪种方式，HTML 必须包含完整的侧边栏目录（TOC 静态生成）、代码复制按钮、日期高亮、响应式布局。

### 3.3 跨模式通用格式规则

以下规则同时适用于单机和集群产物：

**代码块**：
- 所有命令使用 ` ```bash ` 代码块（不省略语言标记）
- YAML 配置使用 ` ```yaml ` 代码块
- JavaScript/MongoDB 命令使用 ` ```javascript ` 代码块
- 纯文本输出使用 ` ```text ` 代码块
- 每个代码块上方必须有**一行说明文字**交代操作目的和执行位置

**表格**：
- 版本信息表格始终排在文档最前面（标题之后）
- 下载链接表格使用两列格式（`| 文件 | 下载链接 |`）
- "提前准备"中的离线下载表格必须列出实际可点击的完整 URL

**引用块**：
- `> ⚠️ **重要提示**`：红色高亮（授权检查、数据备份）
- `> ⚠️ **注意**`：红色高亮（前端二开、镜像改名警告）
- `> ⚠️ **特别注意**`：红色高亮（升级前必须完成的操作）
- `> 💡`：蓝色普通提示（默认路径、命名空间说明）

**编号规则**：
- h3 级编号：`### 1.` / `### 2.` … 仅用于"升级前准备"子节
- h4 级编号：`#### 1.` / `#### 2.` … 用于操作步骤（第一阶段、第二阶段）
- h4 级"N."编号：`#### N. 来自 v{版本}：{说明}` 用于第三阶段版本块

### 3.4 禁止的结构偏离

以下为生成产物时的绝对禁止事项：

- **禁止**在任何章节标题前加上"第X章""Section"等额外前缀
- **禁止**将 h4 改为 h3 或 h5（如 `#### 1. 替换镜像名称` 不能写成 `### 1. 替换镜像名称`）
- **禁止**在"升级后验证"之前插入额外章节
- **禁止**遗漏"异常情况排查"（仅单机模式必须有此节）
- **禁止**在底部声明之后追加任何内容
- **禁止**在 Markdown 产物中保留任何 `{...}` 占位符（所有占位符必须被真实数据替换）
- **禁止**在 Markdown 产物中保留任何 AI 内部注释（如 `【AI 填写说明】`、`{AI 填写说明}`、HTML 注释中的指令）
- **禁止**产物中出现 HTML 标签（Markdown 应为纯文本格式，由 md2html 工具负责 HTML 转换）

## 产物命名规范

生成升级文档时，产物文件名（不含扩展名）统一使用以下中文命名格式：

```
HAP升级指南-v{当前版本}-to-v{目标版本}-{模式}-{架构}
```

其中：
- `{模式}`：`单机`（单机模式）或 `集群`（集群模式）
- `{架构}`：`amd64` 或 `arm64`（**必填，不可省略**）

**示例**：
- `HAP升级指南-v7.1.1-to-v7.3.2-集群-amd64.md`
- `HAP升级指南-v7.0.2-to-v7.3.6-单机-arm64.md`

     # 在 skill 根目录下执行，直接解压到 tools/ 下自动生成 md2html/ 子目录

     ```

> ⚠️ **MongoDB 建库精确扫描与验证流程（强制执行，不可跳过任何步骤）**：
> 
> MongoDB 建库操作极易遗漏（原因是：① 不体现在版本总表 √ 标记中；② 建库命令通常隐藏在页面后半部分的"集群模式附加操作"小节中；③ 网页抓取工具常因页面过长而截断附加操作内容）。因此必须执行以下 **三阶段验证**，**任一阶段未通过不得进入文档写入**。
> 
> **阶段一：逐版本精确扫描**
> 
> 对升级路径中的**每个版本**执行以下两条并行检查：（以下以 `curl` 示例；若运行环境无 `curl`，可用客户端网页抓取工具获取该 URL 的完整原始 HTML 后做等价的关键词检索）
> 
> ```bash
> # 检查 A：MongoDB 相关通用关键词
> curl -sL "https://docs-pd.mingdao.com/upgrade/{版本号}/" | grep -a -i -E "mongodb|mongo |创建数据库|新建数据库|新建库|认证|createUser|use [a-z]"
> 
> # 检查 B：精确匹配已知数据库名（逐个检查，命中即确认该版本需建库）
> curl -sL "https://docs-pd.mingdao.com/upgrade/{版本号}/" | grep -a -i "mdwfplugin"
> curl -sL "https://docs-pd.mingdao.com/upgrade/{版本号}/" | grep -a -i "mdpayment"
> curl -sL "https://docs-pd.mingdao.com/upgrade/{版本号}/" | grep -a -i "mdwfai"
> curl -sL "https://docs-pd.mingdao.com/upgrade/{版本号}/" | grep -a -i "mdopenauth"
> curl -sL "https://docs-pd.mingdao.com/upgrade/{版本号}/" | grep -a -i "mdaisearch"
> ```
> 
> **⚠️ 检查 B 是强制执行的**：不可仅依赖检查 A 的结果。检查 A 可能因页面中"mongodb"出现频率过高而被忽略，检查 B 通过精确数据库名匹配消除漏检风险。
> 
> **阶段二：交叉验证（写入文档前强制执行）**
> 
> 扫描完成后，将发现的数据库列表与下表进行双向交叉验证：
> 
> | 来源版本 | 数据库名 | 验证方式 |
> |---------|---------|---------|
> | v5.8.0 | `mdwfplugin` | 若升级路径覆盖 v5.8.0，文档中**必须**出现该库 |
> | v6.2.0 | `mdpayment` | 若升级路径覆盖 v6.2.0，文档中**必须**出现该库 |
> | v7.0.0 | `mdwfai` | 若升级路径覆盖 v7.0.0，文档中**必须**出现该库 |
> | v7.3.0 | `mdopenauth` | 若升级路径覆盖 v7.3.0，文档中**必须**出现该库 |
> | v7.3.0 | `mdaisearch` | 若升级路径覆盖 v7.3.0，文档中**必须**出现该库 |
> 
> **交叉验证规则**：
> - 若升级路径覆盖了上表中的版本，但扫描阶段未发现对应的数据库 → **必须对该版本重新执行阶段一的检查 A + 检查 B**，确认是否遗漏
> - 若重新扫描后仍无结果 → 该版本的建库操作可能已被更高版本的同类操作覆盖，或该版本页面的建库操作被移到了其他子页面，需进一步抓取确认
> - 若升级路径未覆盖上表中的版本 → 该数据库无需纳入文档（如升级路径为 v6.5.0→v7.3.6，则无需 v5.8.0 的 mdwfplugin）
> - **上表仅覆盖当前已知的建库版本，不排除其他版本也有建库操作。阶段一的扫描结果优于上表：若扫描发现了上表中未列出的建库操作，以上表为依据进行确认后将新条目加入文档**
> 
> **阶段三：文档生成后验证（写入 MD 文件后、生成 HTML 前强制执行）**
> 
> 完成 Markdown 文档写入后，**必须**在文档内容中执行以下 grep 验证：
> 
> ```bash
> # 统计文档中实际出现的 createUser 语句数量 = 实际创建的数据库数
> grep -c "createUser" {生成的MD文件路径}
> # 统计文档中实际出现的数据库名
> grep -c "mdwfplugin\|mdpayment\|mdwfai\|mdopenauth\|mdaisearch" {生成的MD文件路径}
> ```
> 
> 将 grep 结果与阶段二交叉验证的预期数据库列表对比：
> - 若数量一致 → ✅ 通过，可继续生成 HTML
> - 若数量不一致 → **立即排查原因**（哪个数据库遗漏？是否扫描阶段有误？是否写入时丢失？），**修复后方可继续**
> - **禁止在阶段三验证未通过的情况下生成 HTML 或交付文档**

### Step 7. 合并跨版本附加操作

如果跨越多个含附加操作的版本，必须读取并遵循 `references/merge-rules.md`。要把它理解为"合并原则文档"，不是"允许操作类型清单"。

> ⚠️ **起始版本排除规则（强制）**：升级文档中的附加操作，仅纳入**起始版本之后**（不含起始版本）到目标版本（含）之间的所有版本。**起始版本自身的附加操作不纳入文档**——因为用户当前已运行在起始版本，该版本的附加操作在升级到起始版本时已经执行过。
>
> 例如：从 v5.5.0 升级到 v7.3.6，则 v5.5.0 自身的附加操作（如 MongoDB 3.4→4.4 升级）不纳入文档；从 v5.1.0 升级到 v7.3.6，则 v5.1.0 自身的镜像拆分操作不纳入文档。只有当起始版本**低于** v5.1.0/v5.5.0 时，对应特殊操作才触发。

特别注意：

- **创建 MongoDB 数据库**：必须为每个库单独列出完整、可直接执行的命令块（`use 库名` + `db.createUser(...)` 精确填入库名），**禁止使用 `{库名}` 占位符或让读者自行替换**；同类建库操作合并成一次 mongo 登录，各库依次单独展示完整命令
- 存储组件只升级到跨越路径要求的最高版本
- MongoDB 预置数据只执行涉及该操作的最新版本命令
- **升级后脚本必须严格按版本从低到高顺序排列**（数字小的版本在前，数字大的在后。例如 v7.2.0 → v7.2.4 → v7.3.0，而非反过来）。这是强制要求，不得按"最新优先"排列。
- **升级后操作的步骤编号结构（单机和集群通用）**：
  - **整体大步骤**使用 h4 标题（进入文档目录导航），格式为 `#### 1. 进入 config Pod 执行脚本`、`#### 2. 来自 v7.2.0：MongoDB 新增索引` 等（使用阿拉伯数字，更易辨识）
    - **单机模式**第一个大步骤为 `#### 1. 进入微服务容器执行脚本`，后续每个版本一个 h4 标题（如 `#### 2. 来自 v7.2.0：MySQL 新增索引`）
    - **集群模式**第一个大步骤为 `#### 1. 进入 config Pod 执行脚本`，后续每个版本一个 h4 标题（如 `#### 2. 来自 v7.2.0：MongoDB 新增索引`）
  - **版本块内部的子操作编号规则**：
    - 若该版本**只有一个**子操作（如只有 MySQL DDL），**不编子序号**，直接显示命令代码块
    - 若该版本**有多个**子操作（如同时有 fileInit 和 MongoDB DDL），使用 `{主步骤号}.{子序号}` 格式，如 `4.1 更新预置文件`、`4.2 MongoDB 新增索引`
    - **子操作标题应简明描述操作内容**（如"MySQL 新增索引"、"MongoDB 新增索引"），不要只写"MySQL DDL"或"MongoDB DDL"
  - **只保留该版本实际存在的操作**，不存在的子操作不要列出
- **同一版本多个同类操作必须合并到一个代码块**：若某版本有多个库的 MongoDB DDL 或多个 MySQL DDL 文件，将所有命令合并到同一个代码块中逐行列出，禁止每个库/每个文件拆成独立代码块
- 集群新增服务配置需要把多版本新增项合并到同一节里
- **同一版本有多个新增服务（如 platformapi + openauthorization）时，必须合并到同一个 YAML 代码块中**，用 `---` 分隔各服务的 Deployment/Service 定义，禁止拆成多个独立代码块、禁止为每个服务单独添加子标题（如"新增 platformapi 服务："加一个代码块，再"新增 openauthorization 服务："加另一个代码块）
- **集群 service.yaml 的删除和新增服务**：在同一个编号条目中先展示删除块、再展示新增块；**删除块必须从官网抓取到的页面内容中提取完整 YAML 配置**（包含 Deployment 和 Service 的完整字段），禁止用省略号 `...` 或示意性注释代替任何字段；新增块同样完整复制官方 yaml 配置（两件事均展示，不拆分成两个独立步骤）。若涉及多个新增服务，新增部分使用**单个 YAML 代码块**包含全部新增服务。**如果官网页面中该服务的 YAML 配置本身有省略号，必须标注"以下配置以官网实际内容为准，执行时请对照 service.yaml 中实际存在的 pushserver 相关配置删除"，而非直接在文档中输出带省略号的 YAML**
- **同一操作的文字说明必须全局去重**：跨多个版本合并附加操作时，以“操作对象 + 动作 + 目标文件/服务”为唯一键。例如“在 `service.yaml` 中找到并删除 `pushserver` 对应的 Deployment 和 Service 配置段”只能出现一次；如果同一操作同时来自多个版本，只保留一条说明，并在同一代码块或说明中合并其全部实际内容。不得因为版本来源不同而重复输出完全相同的句子、标题或 YAML 配置。
- **集群 service.yaml 中"修改已有 Service"与"新增服务"必须分离**：若官方文档要求对已有 Service（如 `push`）追加端口、修改标签或调整其他配置，**禁止**将该片段与新增完整服务的 YAML 合并到同一个可复制的代码块中。必须：1) 单独作为一个小步骤（如"第二步：修改已有 Service 的端口映射"）；2) 代码块中只保留需要追加/修改的片段（如 `- name: grpc-push` 端口条目）；3) 显式说明"先在 `service.yaml` 中定位到 `metadata.name: xxx` 的 Service，在现有 `ports` 数组中手动添加，禁止直接复制整段追加到文件末尾。**添加时注意缩进**：新条目必须与 `ports` 数组中已有条目保持相同的缩进层级，YAML 对缩进敏感，缩进不一致会导致解析失败"；4) 涉及的服务名称必须准确（如 `push` 不是 `pushserver`），需与官方文档一致
- **ARM64 架构下 service.yaml 镜像处理**：当架构为 ARM64 且 Step 5 架构校验通过时，service.yaml 中**所有展示的镜像名称**（包括新增服务和删除服务的示例 YAML）均需添加 `-arm64` 后缀（如 `mingdaoyun-hap:7.2.4` → `mingdaoyun-hap-arm64:7.2.4`）。删除服务的示例 YAML 虽然不涉及实际镜像拉取，但为了与操作人员实际环境中的 ARM64 镜像名保持一致，同样需要加后缀。**无需添加任何可用性警告或确认提示**——架构校验通过即代表所有镜像已有 ARM64 版本
- **集群命名空间**：模板中所有命令均使用 `default` 作为默认命名空间，提示语改为"若未使用默认命名空间，请将命令中的 `default` 替换为实际的命名空间（namespace）"
- **集群 fileInit 操作**：必须展示三点说明（参见下方"fileInit 规范"）

                    } catch (e) {
                        print(`  └─ ✗ Error: ${e.message}`);
                        print("     Skipping this index...\n");
                    }
                });

            printHeader("Process Completed");

### 6. 预置文件（preset_file）下载地址规范

> ⚠️ **适用条件**：仅当本次升级路径中至少一个版本的升级详情页明确要求 fileInit（预置文件初始化）时，才需要获取预置文件下载链接。如果所有版本详情页均未提及 fileInit，则**不列**。

**URL 格式**：

```
https://pdpublic.mingdao.com/private-deployment/data/preset_file_{版本号}.tar.gz
```

**版本号确定方法**（必须根据实际情况动态确定，禁止硬编码）：

1. **扫描升级路径**：在 Step 6 逐版本扫描阶段，对每个版本详情页搜索 `fileInit`、`s3fileInit`、`预置文件`、`重新初始化` 等关键词，记录哪些版本要求执行 fileInit
2. **合并规则**：fileInit 遵循与 MongoDB 预置数据相同的"仅执行最新版本"合并规则——取升级路径中**包含 fileInit 操作的最高版本号**
3. **构造 URL**：将确定的版本号代入 URL 格式中的 `{版本号}`（不带 `v` 前缀），例如路径中含 fileInit 的最高版本为 7.3.0，则下载链接为 `https://pdpublic.mingdao.com/private-deployment/data/preset_file_7.3.0.tar.gz`

**适用场景**：

| 场景 | 是否需要 preset_file 下载链接 | 说明 |
|------|------|------|
| 离线模式 + fileInit | ✅ 需要 | 离线环境下无法从容器内联网拉取，必须提前下载并上传 |
| 联网模式 + fileInit 情况 1（内置存储） | ❌ 不需要 | `fileInit` 命令在容器内直接执行，自动拉取预置文件 |
| 联网模式 + fileInit 情况 2（MinIO） | ❌ 不需要 | `s3fileInit` 命令在容器内直接执行，自动拉取预置文件 |
| 联网模式 + fileInit 情况 3（外部 S3） | ✅ 需要 | 需手动下载预置文件包并上传到对象存储 bucket |

**禁止**：
- 禁止在离线场景下省略 `preset_file` 下载链接
- 禁止使用硬编码版本号构造 URL，必须根据升级路径实际扫描结果确定
- 禁止将 `preset_file` 与 `preset_mongodb` 混为同一资源（前者是文件预置数据，后者是 MongoDB 预置数据，URL 前缀不同）
- 禁止在"提前准备"表格中将 `preset_file` 拆为多行（同一版本只需一个 preset_file 包）

## 生成升级指南时的要求

### 1. 先选模板（强制）

> ⚠️ **模板是产物结构的唯一事实来源，不可绕过。**

根据部署模式读取 Markdown 模板：

- 单机模式：读取（如 WorkBuddy 的 Read 工具，或等效文件读取能力） `assets/upgrade-guide-template-standalone.md`
- 集群模式：读取（如 WorkBuddy 的 Read 工具，或等效文件读取能力） `assets/upgrade-guide-template-cluster.md`

**禁止**脱离模板凭记忆重写整个结构。**禁止**只读模板的部分内容。必须完整读取模板全文，确保模板中的每个章节注释、条件提示都被理解后再开始填充。HTML 无需读取模板，由脚本从 MD 自动生成（见下文 2.3 节）。

### 2. 再填内容

#### 2.1 Markdown 文档结构要求

Markdown 是唯一事实来源，HTML 从它自动生成，因此 Markdown 内容必须完整、正确。

**文档必须包含以下章节（按顺序）**：
1. 标题（`# HAP 升级指南（单机/集群模式）`）
2. 版本信息表格（两列表格：升级路径、部署模式、架构、网络、生成日期）
3. 提前准备
4. 升级前准备（必须包含"授权有效期检查"和"前端二开注意事项"两个小节，分别列为第一项和第二项，即便无其他步骤也要保留此两节）
5. 升级步骤
   - 第一阶段：HAP 微服务升级前操作
   - 第二阶段：升级微服务
   - 第三阶段：HAP 微服务升级后操作
6. 升级后验证
7. 参考文档
8. 底部声明（AI 生成声明）

单机模式还包含"异常情况排查"章节；集群模式不包含此章节。

**"参考文档"章节动态裁剪规则**：

文档末尾的"参考文档"章节**禁止**硬编码全量链接列表。必须按本次升级路径**实际涉及的操作**动态裁剪：

- 始终保留的链接（所有升级路径通用）：
  - 版本发布历史（`/version`）
  - 离线资源包（`/deployment/offline`）
  - 微服务升级（对应各自模式）
  - 常见问题 FAQ（`/faq/deployment`）

- 条件保留的链接（仅当本次升级**实际涉及**该操作时才列出）：
  - 数据备份文档：仅在升级前准备章节有数据备份操作时保留（但数据备份是必做项，通常都保留）
  - MongoDB 预置数据更新：仅在本次升级路径含此操作时保留
  - MongoDB 新建数据库：仅在本次升级路径含此操作时保留
  - 其他特定操作对应的参考文档

- **禁止**列出本次升级未涉及的操作对应的参考文档链接（如本次升级无预置数据操作，就不列出预置数据的参考链接）

#### 2.2 Markdown 文档填充规则

填充 Markdown 文档时，遵守以下规则：

- 文档顶部信息必须补全升级路径、部署模式、架构、网络情况、生成日期，**必须使用两列 Markdown 表格格式**（禁止使用行内加粗键值对格式，因为会挤在一起）。格式示例：
  ```markdown
  | 项目 | 内容 |
  |------|------|
  | **升级路径** | v4.8.1 → v7.2.1 |
  | **当前版本发布日期** | {从/version总表实时抓取} |
  | **目标版本发布日期** | **{从/version总表实时抓取}** ⚠️ |
  | **部署模式** | 单机模式（Docker Compose） |
  | **服务器架构** | AMD64 |
  | **服务器网络** | 可访问互联网 |
  | **文档生成日期** | 2026-03-30 |
  ```
- 备份步骤必须保留在最前面
- "提前准备"必须汇总**本次升级实际会用到的全部资源**，不限于 HAP 微服务镜像。但每个资源都必须能在本次升级路径中至少一个版本的升级详情页找到依据——**禁止根据"其他升级路径需要"或"历史惯例"进行推断式添加**。未出现在任何版本详情页中的组件离线包（如 doc/ldoc/file 存储服务），不得列入
- 如果某一阶段完全没有步骤，删除整节，不保留占位提示
- **第一阶段步骤编号必须显式重排**：两个模板中的第一阶段步骤编号（1. 替换镜像名称、2. 创建 MongoDB 数据库、3. 存储组件升级 / 更新 service.yaml、4. MongoDB 预置数据更新）是固定示例。实际生成文档时，必须根据本次升级路径**实际涉及的操作**进行编号重排：
  - 若某步骤不适用（如升级路径无镜像改名），后续步骤编号应**顺次前移**（如原来编号 3 的操作变成编号 2），不得保留编号空位
  - 重排后的编号必须**连续**（1, 2, 3, ...），不得出现跳跃（如 1, 4）
  - 此规则同时适用于单机和集群两套模板
- 所有命令必须给出完整代码块，不能写"同上""省略""按前文类似处理"
- 生成的是面向执行者的文档，不要把模型的推理过程写进正文
- **禁止**在产物中出现任何面向 AI 自身的指令性免责文本或元信息说明，这些仅作为内部约束，不输出给用户。包括但不限于：
  - "不要预设资源类型已经列全""如本次升级还涉及其他离线镜像或资源，请继续补充"
  - "⚠️ 特别注意：本次升级跨越 N 个含附加操作的版本（vX.X.X、vX.X.X、...），必须按本文档合并后的步骤依次完成，不可跳过"
  - "本次升级共跨越 X 个版本，其中 Y 个含附加操作"
  - 任何涉及"合并"（merge）逻辑的说明文字（如"已合并""按合并规则执行""低版本操作已省略"等属于 AI 内部决策过程，不应暴露给用户）
- 如果线上文档把附加操作写成超链接或跳转说明，最终输出时必须把超链接背后的实际步骤展开写入对应章节，不能只给一个链接让用户自己点进去
- **微服务升级必须包含 ENV_APP_VERSION 变量值设置**：
  - **单机模式**：在"第二阶段：升级微服务"的"修改镜像版本号"步骤中，必须同时说明：
    * 修改 `docker-compose.yaml` 中的 HAP 镜像版本号
    * 确保 `ENV_APP_VERSION` 环境变量的值与微服务镜像版本号保持一致（例如：微服务版本是 7.1.1，`ENV_APP_VERSION` 的值也应设为 7.1.1）

      image: registry.cn-hangzhou.aliyuncs.com/mdpublic/mingdaoyun-hap:4.8.1
      environment:
        ENV_APP_VERSION: "4.8.1"

      # 修改后
      image: registry.cn-hangzhou.aliyuncs.com/mdpublic/mingdaoyun-hap:6.2.0
      environment:
        ENV_APP_VERSION: "6.2.0"
      ```
  - **集群模式**：在"第二阶段：升级微服务"的升级步骤中，必须同时说明：
    * `update.sh update hap {目标版本号}` 命令会自动更新镜像版本号
    * `ENV_APP_VERSION` 环境变量也会通过 update.sh 自动更新为相同的版本号
    * 如果需要手动确认，可以查看部署的 yaml 文件或 Pod 环境变量进行验证

  **第一项：授权有效期检查**（编号为第 1 步）
  - **标题**：`授权有效期检查`
  - **必须标注重要提示**，使用 `> ⚠️` 引用块

    * 若授权即将到期或已过期，请联系明道云商务团队续期后再执行升级
  - ⚠️ **日期填充强制约束**：生成文档时，授权有效期检查段落中的日期**必须与版本信息表格中的「目标版本发布日期」单元格完全一致**（即目标版本如 v7.3.6 的发布日期）。**严禁**单独引入"目标主版本发布日期"（如 v7.0.0 的日期）或在授权段落中填写不同于表格目标版本日期的值。**严禁保留占位符**。
  - **固定提示语**（必须包含，其中 `{目标版本日期}` 由 AI 替换为版本信息表格中已填入的「目标版本发布日期」真实值）：

#### 2.3 HTML 文档生成

**MD 是唯一事实来源。**

生成 Markdown 文档后，按以下优先级转换为 HTML（工具可用性已在 **Step 0** 中确认）：
1. **优先使用本地 `md2html` 工具（Go 二进制）**：若 Step 0 确认 `tools/md2html/` 目录下有编译好的二进制（Windows: `md2html.exe`，macOS/Linux: `md2html`），直接调用：`md2html -input xxx.md -output xxx.html`
2. **回退使用 `md2html-py` 脚本（Python 版）**：若 Go 二进制不可用但 Step 0 确认 `tools/md2html-py/md2html.py` 存在且环境有 `python3`（或 `python`），调用：`python3 tools/md2html-py/md2html.py -input xxx.md -output xxx.html`（若命令为 `python` 则相应替换）。该脚本与 Go 版共用 `template.html`，产出的 HTML **字节级一致**
3. **若两者均不可用**：无需再次询问用户（Step 0 已输出 fallback 提示），直接用 AI 读取 MD 内容按 CSS/JS 规范手工转换并写入 `.html` 文件

**md2html 工具跨平台编译说明**（Go 版工具丢失或需重新编译时使用）：
- 完整工具包在 `tools/md2html-tools.tar.gz`（含源码 + 编译产物 + 依赖），可直接解压使用
- 源码文件：`tools/md2html/main.go`、`tools/md2html/template.html`
- 依赖：Go 1.26+，安装后执行 `go build -o md2html.exe main.go`（Windows）或 `go build -o md2html main.go`（macOS/Linux）
- `template.html` 通过 `//go:embed` 在编译时嵌入二进制，修改模板后必须重新编译
- 该工具不依赖外部运行时，编译后的单文件二进制可在对应平台独立运行
- 第三方依赖：`goldmark`（Markdown 解析）、`goquery`（HTML DOM 操作），首次编译需联网 `go mod download`

**md2html-py 脚本说明**（无 Go 运行时 / codex 等客户端首选，无需编译）：
- 脚本文件：`tools/md2html-py/md2html.py`（纯 Python 标准库实现，**零第三方依赖**，只需运行环境有 `python3`（或 `python`））
- 与 Go 版共用 `tools/md2html/template.html`（模板是唯一 CSS/JS 出处，两版同源），因此对相同 Markdown 输入产出**字节级一致**的 HTML
- 调用方式：`python3 tools/md2html-py/md2html.py -input <输入.md> -output <输出.html>`（若环境中命令为 `python` 则相应替换；参数 `-input` / `-output` 与 Go 版一致）
- **适用场景**：客户端无 Go 工具链、Go 二进制解压失败、或希望免编译跨平台运行时——此时用 Python 脚本即可获得与 WorkBuddy Go 版完全相同的产物，保证多客户端输出统一

**md2html 工具功能说明**（AI 直接转换时需同等实现）：
- 使用 goldmark 解析 Markdown，支持 GFM、定义列表、任务列表
- 代码块自动添加语言标签和复制按钮
- heading ID 自动修正：去掉标题开头的 `数字. ` 前缀，确保 id 不以数字开头（如 `1. 确认服务状态` → `id="确认服务状态"`）
- TOC 目录**静态生成**（非 JS 动态生成），确保链接和 heading id 严格匹配
- 目录链接使用**原生 anchor 导航**，**禁止**使用 `e.preventDefault()` + `getElementById()` / `scrollIntoView()` 人工跳转（原生 anchor 在所有浏览器中 100% 可靠）
- 首个表格自动标记 `class="meta-block"`
- 含 ⚠️ 的引用块自动标记 `class="attention"`
- 表格内日期高亮（`.date-val` / `.date-val-primary`）
- 正文内日期高亮（`.inline-date`）
- 正文内容前导空白自动 trim

**TOC 静态生成算法**（AI 直接转换时必须严格遵循，确保任何客户端效果一致）：

TOC 必须在生成 HTML 时**静态构建**，直接输出到 `<ul class="toc" id="toc">` 内部（`{{TOC}}` 占位符位置）。**禁止**留空让 JS 动态生成。

算法步骤：
1. 遍历正文中的所有 heading（h2~h5），按文档顺序
2. 对每个 heading，生成对应的 id（规则：去掉开头数字编号前缀，如 `2. 升级前准备` → `id="升级前准备"`）
3. 将 heading 组织为**两级结构**：h2 为一级条目（`toc-section`），h3/h4/h5 为其子项（`toc-children`）
4. 输出 HTML 规则：
   - **h2 条目**：输出 `<li class="toc-section"><div class="toc-header"><button class="toc-toggle">▾</button><a href="#{id}">{标题文字}</a></div><ul class="toc-children">`，后续 h3/h4/h5 作为子项
   - **h3 子项**：输出 `<li class="h3"><a href="#{id}">{标题文字}</a></li>`
   - **h4 子项**：输出 `<li class="h4"><a href="#{id}">{标题文字}</a></li>`
   - **h5 子项**：输出 `<li class="h5"><a href="#{id}">{标题文字}</a></li>`
   - **h2 section 关闭**：当遇到下一个 h2 或遍历结束时，输出 `</ul></li>`
   - **⚠️ 严禁**在 `<ul>` 内使用 `<div>` 作为子元素，所有条目必须是 `<li>`

示例输出结构（节选）：
```html
<ul class="toc" id="toc">
  <li class="toc-section"><div class="toc-header"><button class="toc-toggle">▾</button><a href="#升级前准备">升级前准备</a></div>
    <ul class="toc-children">
      <li class="h3"><a href="#检查授权有效期">检查授权有效期</a></li>
      <li class="h3"><a href="#备份数据">备份数据</a></li>
    </ul>
  </li>
  <li class="toc-section"><div class="toc-header"><button class="toc-toggle">▾</button><a href="#升级执行">升级执行</a></div>
    <ul class="toc-children">
      <li class="h3"><a href="#第一阶段">第一阶段：存储组件升级</a></li>
    </ul>
  </li>
  <li class="toc-section"><div class="toc-header"><button class="toc-toggle">▾</button><a href="#升级后验证">升级后验证</a></div><ul class="toc-children"></ul></li>
  <li class="toc-section"><div class="toc-header"><button class="toc-toggle">▾</button><a href="#参考文档">参考文档</a></div><ul class="toc-children"></ul></li>
</ul>
```

**关键约束**（违反会导致 TOC 点击失效）：
- 每个 `toc-section` 的 `<li>` 必须**正确闭合**（`</ul></li>`）
- 最后一个 `toc-section` 同样必须闭合，**不能**遗漏
- **禁止**使用 `e.preventDefault()` 拦截链接点击，必须使用原生 anchor 导航
- **禁止**使用 `document.querySelector` 选择以数字开头的 id，必须用 `document.getElementById`

无论哪种方式，转换后的 HTML 必须严格遵守以下规范：

(function() {

        toggle.textContent = '✕ 关闭';

      } else {
        closeSidebar();
      }
    }
  });

  // 侧边栏内关闭按钮
  if (closeBtn) {
    closeBtn.addEventListener('click', closeSidebar);
  }

  // 点击遮罩关闭侧边栏（移动端）
  if (overlay) {
    overlay.addEventListener('click', closeSidebar);
  }

  // 初始化：桌面端 sidebar 展开时隐藏 toggle，移动端始终显示
  if (!isMobile() && !sidebar.classList.contains('collapsed')) {
    toggle.style.display = 'none';
  }
  toggle.textContent = isMobile() ? '☰ 目录' : '◀ 收起目录';

  // 窗口尺寸变化时重置状态
  window.addEventListener('resize', function() {
    if (!isMobile()) {
      sidebar.classList.remove('open');
      if (overlay) overlay.classList.remove('active');
      // 桌面端：sidebar 展开则隐藏 toggle，折叠则显示 toggle
      toggle.style.display = sidebar.classList.contains('collapsed') ? 'block' : 'none';
    } else {
      sidebar.classList.remove('collapsed');
      if (main) main.classList.remove('expanded');
      toggle.style.display = 'block';
    }
    toggle.textContent = isMobile() ? '☰ 目录' : '◀ 收起目录';
  });
})();

(function() {
  var toc = document.getElementById('toc');
  if (!toc) return;

  // 折叠按钮事件
  document.querySelectorAll('.toc-toggle').forEach(function(toggle) {
    toggle.addEventListener('click', function(e) {

  // 点击目录链接 —— 不拦截原生 anchor 跳转，让浏览器自行导航（100% 可靠）

  var allLinks = toc.querySelectorAll('a');
  var justClicked = false;
  var clickTimer = null;
  allLinks.forEach(function(a) {
    a.addEventListener('click', function(e) {
      // 立即高亮当前点击项，移除其他项高亮
      allLinks.forEach(function(link) { link.classList.remove('active'); });
      a.classList.add('active');

      // 锁定 scroll 高亮更新，防止 anchor 跳转过程中 scroll 事件覆盖 active
      justClicked = true;
      if (clickTimer) clearTimeout(clickTimer);
      clickTimer = setTimeout(function() { justClicked = false; }, 400);

      var isMob = window.innerWidth <= 768;
      if (isMob) {
        setTimeout(function() {
          var sb = document.querySelector('.sidebar');
          if (sb) sb.classList.remove('open');
          var ov = document.querySelector('.sidebar-overlay');
          if (ov) ov.classList.remove('active');
          var tg = document.querySelector('.sidebar-toggle');
          if (tg) tg.textContent = '☰ 目录';
        }, 200);
      }
      // 桌面端：完全不拦截，原生 anchor 跳转 + 点击时即时高亮 + scroll 锁定
    });
  });

  // 滚动高亮当前章节
  var headings = document.querySelectorAll('.content h2, .content h3, .content h4, .content h5');
  function onScroll() {
    if (justClicked) return; // 点击后短时间内跳过 scroll 高亮更新，避免被覆盖
    var scrollY = window.scrollY + 80;
    var active = null;
    headings.forEach(function(h) { if (h.offsetTop <= scrollY) active = h.id; });
    allLinks.forEach(function(a) { a.classList.toggle('active', a.getAttribute('href') === '#' + active); });
  }
  window.addEventListener('scroll', onScroll, { passive: true });
  onScroll();
})();

**代码块特别要求**（最关键，不得出错）：
- 所有代码内容**必须原样保留**，不得截断、省略或改写，不论代码有多长（包括 4000+ 字符的 JS 脚本）
- `<` `>` `&` `"` 需 HTML 转义为 `&lt;` `&gt;` `&amp;` `&quot;`
- `data-lang` 属性值为代码块语言标识（如 `bash`、`yaml`、`javascript`），无语言标识时写 `data-lang=""`
- **禁止**用 `...` 或 `省略` 代替代码内容
- **禁止**在代码块中插入换行符或修改缩进

**标题 id 生成规则**：取标题文字，**先去掉开头的数字编号前缀**（如 `1. `、`2. `、`1、` 等），然后保留中文和字母数字，空格转 `-`，其余字符删除，全部小写。例：`1. 确认服务状态` → `id="确认服务状态"`；`第二阶段：HAP 微服务升级前操作` → `id="第二阶段hap-微服务升级前操作"`

**禁止事项**：
- 禁止手动填充任何旧 HTML 模板
- 禁止省略或截断任何代码块内容
- 禁止在输出 HTML 前将文件交给用户（必须先写入文件）
- **AI 直接转换 HTML 时，严禁使用未经用户确认的本地 Python/Node.js 脚本**（即禁止临时编写/调用与本项目无关的脚本）；但本 Skill 自带的 `tools/md2html-py/md2html.py` 是**受信任的转换工具**，可直接调用而无需额外确认；优先顺序是 Go 二进制 → `md2html-py` 脚本 → AI 手工转换，三者均产出一致的 HTML

### 5. 针对不同部署模式的硬规则

- **存储组件（SC）升级仅限单机模式**：集群模式（Kubernetes）下 Kafka/Redis/etcd 等中间件由 K8s 原生管理，不存在 SC 组件概念。**禁止在集群模式文档中生成任何 SC 相关内容**（包括离线包、docker load 命令、升级步骤、参考文档链接等）
- 单机模式不能生成 `kubectl`、`crictl`、`ctr` 命令
- 集群模式不能生成 `docker exec`、`service.sh restartall` 这类单机命令
- ARM64 时，涉及镜像名或更新命令时，必须检查是否需要 `-arm64`
- **ARM64 service.yaml 镜像处理**：当架构为 ARM64 且升级路径中含 service.yaml 操作时，YAML 配置中**所有展示的镜像名称**（无论新增还是删除服务的示例）均需添加 `-arm64` 后缀（如 `mingdaoyun-platformapi` → `mingdaoyun-platformapi-arm64`、`mingdaoyun-hap:7.2.4` → `mingdaoyun-hap-arm64:7.2.4`）。架构校验（Step 5）已通过即代表所有镜像均有 ARM64 版本，**禁止**在文档中添加任何 ARM64 镜像可用性警告或确认提示
