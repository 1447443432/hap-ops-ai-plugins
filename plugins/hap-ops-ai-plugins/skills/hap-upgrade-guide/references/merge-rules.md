# HAP 升级附加操作合并规则

本文件提供的是**附加操作合并原则和典型示例**，不是操作类型白名单。

使用时遵循以下原则：

- 实际有哪些附加操作，必须以本次升级路径中抓取到的**线上升级说明页原文**为准
- 本文件中未列出的操作类型，只要在线上升级说明页中出现，也必须纳入分析和文档生成
- 遇到新操作类型时，先判断它属于“升级前操作”还是“升级后操作”，再按照其执行时机、是否可合并、是否需要保留顺序来整理
- 如果某类操作在线上文档中明确要求“仅执行最新版本一次”“按版本顺序逐条执行”“需合并为一次修改”，必须优先遵循线上文档原意
- 本文件中的表格和示例用于帮助模型理解常见合并模式，不能据此否定线上文档实际出现的其他操作

跨多个含附加操作的版本时，必须按照以下原则将所有版本的附加操作合并为一次执行或整理为有序步骤。

## 1. HAP 微服务升级前操作合并原则与示例

| 示例操作类型 | 合并方式 |
|----------|----------|
| **创建 MongoDB 数据库** | 合并为一次登录，一次性创建所有需要的库。**必须执行阶段一（curl 逐版本扫描）+ 阶段二（交叉验证表对账）+ 阶段三（文档后 grep 验证），详见 SKILL.md Step 6「MongoDB 建库精确扫描与验证流程」** |
| **存储组件升级（仅单机）** | 直接升级到所有跨越版本中要求的**最高版本** |
| **MongoDB 预置数据更新** | 仅执行跨越路径（含目标版本）中，**包含此操作的最新版本**的命令，无需执行中间版本或不含此操作的版本 |
| **微服务 yaml 新增服务配置（集群）** | 合并所有版本需新增的服务，一并写入 yaml。**YAML 内容必须完整，禁止用省略号 `...` 代替任何字段；若官网页面本身含省略号，需标注"以 service.yaml 实际配置为准"** |

> ⚠️ **ARM64 架构下 service.yaml 新增服务镜像处理**：当架构为 ARM64 时，新增服务 YAML 中的镜像名称必须添加 `-arm64` 后缀（如 `mingdaoyun-platformapi` → `mingdaoyun-platformapi-arm64`）。架构校验（Step 5）已通过即代表所有镜像均有 ARM64 版本，**禁止**在文档中添加任何可用性警告或确认提示。详见 SKILL.md Step 5 及「针对不同部署模式的硬规则」中 ARM64 相关条目。

若线上文档出现其他升级前操作，按以下思路处理：

| 判断维度 | 处理原则 |
|----------|----------|
| **是否可以合并为一次环境进入 / 一次文件修改 / 一次配置变更** | 能合并则合并，减少重复进入容器、重复编辑文件或重复重启 |
| **是否要求使用最新版本对应资源** | 若线上文档明确只需执行最新版本对应资源，则不要重复执行中间版本的同类步骤 |
| **是否依赖原版本运行状态** | 若线上文档要求在原版本服务运行状态下执行，必须放在 HAP 微服务升级前 |

> ⚠️ **MongoDB 建库版本-库名对照参考表**：以下为当前已知需创建 MongoDB 数据库的版本及对应数据库名。此表用于交叉验证阶段的"双向对账"——若升级路径覆盖以下版本，则对应数据库**必须**出现在文档中；若扫描发现了表中未列出的建库操作，以扫描结果为准并入表。

| 来源版本 | 数据库名称 | 说明 |
|---------|-----------|------|
| v5.8.0 | `mdwfplugin` | 工作流插件 |
| v6.2.0 | `mdpayment` | 支付服务 |
| v7.0.0 | `mdwfai` | AI 工作流 |
| v7.3.0 | `mdopenauth` | 开放认证 |
| v7.3.0 | `mdaisearch` | AI 搜索 |
| v7.4.0 | `MDAgentInfra` | 智能体基础设施（Agent 相关，单机/集群均可能在开启 MongoDB 认证时要求新建） |

**注意**：此表不保证完整覆盖所有历史版本。生成文档时仍需以 SKILL.md Step 6 的阶段一扫描结果为准。

## 2. HAP 微服务升级后操作合并原则与示例

| 示例操作类型 | 合并方式 |
|----------|----------|
| **进入容器执行 MySQL DDL（单机）** | 一次进入容器，按版本从低到高顺序执行所有版本的 DDL |
| **进入 config Pod 执行脚本（集群）** | 一次进入 Pod，按版本从低到高顺序执行所有版本的命令 |
| **fileInit / s3fileInit（预置文件初始化）** | 仅执行跨越路径中包含此操作的**最高版本**对应的命令，低版本的 fileInit 省略。fileInit 与 MongoDB 预置数据遵循相同的"仅执行最新版本"合并规则。 |

> ⚠️ **非 MySQL 数据库 DDL 替换**：当用户指定使用非 MySQL 关系型数据库（如达梦 DM、OceanBase、KingbaseES 等）时，上述合并规则中的"MySQL DDL"需替换为对应数据库的 DDL。替换规则详见 SKILL.md「关系型数据库变更 DDL（非 MySQL 场景）」章节。合并原则不变——仍按版本从低到高排列、一次连接数据库后连续执行所有版本的 DDL。**MongoDB DDL、文件初始化等非关系型数据库操作不受影响。**
>
> ⚠️ **步骤编排变更（非 MySQL 场景）**：非 MySQL DDL **不进入 HAP 容器 / config Pod**，与容器/Pod 内的操作（MongoDB DDL、fileInit、预置数据脚本等）**分开编排为独立步骤**。
>
> **集群模式**升级后操作结构示例：
> - `#### 1. 进入 config Pod 执行脚本` → 仅含 MongoDB DDL、fileInit 等需在 Pod 内执行的操作
> - `#### 2. 在{数据库名}数据库中执行 DDL 变更` → 直接给出 `disql`/`ksql` 等连接命令 + 按版本从低到高排列的 DDL，**不含 kubectl 命令**
>
> **单机模式**升级后操作结构示例：
> - `#### 1. 进入微服务容器执行脚本` → 仅含预置数据脚本等需在 HAP 容器内执行的操作
> - `#### 2. 在{数据库名}数据库中执行 DDL 变更` → 直接给出数据库连接命令（如 `docker exec -it {达梦容器名} disql ...` 或 `disql {用户}/{密码}@{IP}:5236`）+ DDL 内容，**不含进入 HAP 微服务容器的 `docker exec -it $(docker ps | grep mingdaoyun...)` 命令**

若线上文档出现其他升级后操作，按以下思路处理：

| 判断维度 | 处理原则 |
|----------|----------|
| **是否必须保留版本顺序** | 只要脚本或 DDL 具备明显版本递进关系，就按版本从低到高排列 |
| **是否可以在一次进入容器 / Pod 后连续执行** | 能合并执行环境进入动作时，不要拆成多次进入 |
| **是否存在多种脚本类型** | 按线上文档实际分类保留，例如 MySQL DDL、MongoDB DDL、文件初始化等，不要混写成单一类型 |

## 3. 合并示例

**场景：从 v6.4.0 跨越到 v7.2.0（跨过 v6.5.0、v7.0.0、v7.1.0、v7.2.0，均含附加操作）**

*   **升级前合并**：镜像命名替换执行一次（v7.1.0）、MongoDB 库一次性全部创建、MongoDB 预置数据更新至含有该操作的最新版本（如路径中只有 v7.0.0 有此操作，则更新至 v7.0.0）、yaml 新增服务合并写入。
*   **升级后合并（集群）**：一次进入 config Pod，依次执行 v6.5.0 → v7.0.0 → v7.2.0 的所有脚本。

> 以上仅为示例。若本次升级路径中在线上文档遇到未在本文件列出的附加操作，仍应据实提取并按实际执行逻辑合并。

## 4. 特殊历史版本操作

以下两个版本的操作类型较为特殊，不属于常规的"建库 / DDL / 预置数据 / service.yaml"分类。merge-rules.md 本身不对其合并规则做展开，而是由 SKILL.md 提供完整规范。当升级路径跨越这些版本时，请以 SKILL.md 为准：

| 版本 | 特殊操作 | 合并规则 | 详细规范 |
|------|---------|---------|---------|
| **v5.1.0** | Docker 镜像拆分（mingdaoyun → mingdaoyun-community + mingdaoyun-cache） | 仅执行一次（单机+集群均适用），不因跨多版本而重复。**仅当起始版本低于 v5.1.0 时触发；起始版本 ≥ v5.1.0 时不纳入** | 见 SKILL.md「v5.1.0 镜像拆分操作规范」 |
| **v5.5.0** | MongoDB 升级（3.4 → 3.6），含 FCV 转换和认证启用 | 仅执行一次（集群模式可能需特殊处理）。**仅当起始版本低于 v5.5.0 时触发；起始版本 ≥ v5.5.0 时不纳入**（该操作在升级到 v5.5.0 时已执行） | 见 SKILL.md「v5.5.0 MongoDB 升级特殊操作规范」 |

> ⚠️ 生成升级文档时，**不能只读 merge-rules.md** 就判断跨版本操作。遇到 v5.1.0 或 v5.5.0，必须回到 SKILL.md 阅读完整的操作步骤和注意事项。
>
> ⚠️ **起始版本排除规则**：上述特殊操作的触发条件为"起始版本低于该版本"。如果起始版本本身等于或高于 v5.1.0/v5.5.0，则对应特殊操作**不纳入文档**——用户在升级到起始版本时已执行过该操作。
