# HAP 升级文档详细规则

## 逐版本采集

## 文件命名

- Markdown 和 HTML 必须同名，仅扩展名不同：`HAP升级指南-v{当前版本}-to-v{目标版本}-{单机|集群}-{amd64|arm64}.md/.html`。
- 禁止使用下划线命名、`_离线` 后缀、架构大写或省略版本号前的 `v`；离线是文档参数，不进入文件名。

- 当前版本到目标版本之间的所有版本逐一检查，不只检查版本总表有标记的版本。
- 每个版本完整检查“升级说明”、注意框、警告、配置片段、代码块、列表、表格和参考链接。
- 参考链接必须继续抓取并展开为可执行命令、配置修改和验证步骤。
- 未明确说明升级后时机的可执行注意事项归入升级前附加操作，并在文档中说明这是按时机缺失作出的保守分类。

## 附加操作顺序与标题

- 升级前和升级后分别按来源版本号升序排列。
- 同一版本内保持官方页面顺序，不按操作类别、抓取顺序或最新优先重排。
- 每个附加操作标题使用 `#### N. 来自 vX.Y.Z：功能说明`。
- 同类操作合并时，标题列出全部来源版本并按升序排列；不得只写“新增索引”“更新配置”。
- 合并操作只能合并执行方式，不能删除任一版本的命令、前置条件、警告或验证。

## 升级后操作与验证边界

- `第三阶段：HAP 微服务升级后操作` 只收录升级完成后必须执行的变更或附加操作：数据库 DDL/索引、预置数据、文件初始化、配置调整、服务配置变更、重新授权等。
- 服务状态、容器或 Pod 状态、日志、登录版本、业务功能检查属于验证，必须放在 `## 升级后验证`，不得写入第三阶段。
- “进入微服务容器执行脚本”和“进入 config Pod 执行脚本”只是执行后置变更的入口。若没有任何真实的版本后置变更，删除整个第三阶段，不得只留下入口命令。
- `功能验证`模块必须且只能包含以下四项，顺序不可调整：
  1. `- [ ] 打开工作表，创建/编辑记录`
  2. `- [ ] 触发工作流，检查执行情况`
  3. `- [ ] 检查统计图、报表等功能`
  4. `- [ ] 检查附件上传、下载和预览功能`
- 禁止在功能验证中追加外层代理、AI Agent、SSE、长连接或其他业务验证项；基础服务状态、日志和版本检查仍保留在各自的验证步骤。

## 模式隔离

单机文档禁止 `kubectl`、`crictl`、`ctr`、Pod 术语和集群 YAML。集群文档禁止 `docker exec`、`docker-compose`、`service.sh restartall`。集群不存在单机 SC 存储组件内容；单机不能套用集群 file 或 Kubernetes 命令。

## 单机特殊规则

- 数据备份只保留强制提示和官方备份 URL，不生成任何备份命令。
- “5. 检查资源”必须逐句、按原顺序复用 WorkBuddy 单机成品，不得概括或重排：磁盘空间；离线时的目标 HAP 离线镜像经 `docker images` 校验、`preset_mongodb_docker.sh` 与对应 `preset_mongodb_{版本}.tar.gz` 已上传同目录、已安排升级窗口且升级期间不执行其他 HAP 变更；随后原样保留“建议在升级前记录以下现场信息，便于出现异常时与升级前状态对比：”、四条基线清单和“执行操作时，所有默认路径都必须以现场实际配置为准……”的完整结尾说明。
- 现场基线四项必须覆盖：容器名称与状态；`docker-compose.yaml` 的镜像标签、数据目录挂载和外部代理配置；系统登录地址、组织授权状态和前端二开发布状态；备份文件实际保存位置、文件名和完整性校验结果。在线模式仅删除离线资源校验项。
- 第二阶段使用 h4：`#### 1. 修改镜像版本号`、`#### 2. 重启服务`。
- 第一阶段每个操作保留来源版本、执行时机、适用条件、默认路径、完整命令和验证。
- 外部 S3/OSS/COS/OBS 只有官方本次路径明确要求时才出现；提前准备列出 `preset_file` 裸 URL，并注明“仅外部 S3 时执行”。

## 集群特殊规则

- 集群“升级前准备”第 1 项必须使用 WorkBuddy 集群成品的完整授权提示（“若目标版本（日期）晚于授权到期日”）；第 2 项必须逐条保留完整警告、说明、三步列表和结尾，禁止套用单机文案、语义改写或压缩。第 3 项必须写明 MongoDB、文件存储服务及其他有状态服务，禁止出现单机备份链接或“请参考官方备份与部署文档执行备份”。
- “5. 检查资源”必须且只能包含三项：确认各节点磁盘空间充足；确认控制节点可正常执行 `kubectl` 命令；若计划使用滚动更新，确认各微服务节点有约 40% 可用内存，不满足则使用非滚动更新。不得改成单机 Docker 检查，也不得把服务状态或业务功能验证塞入此节。
- `service.yaml` 删除废弃服务、修改已有 Service、新增 Service 必须拆成独立步骤。
- 删除服务必须给出官方完整 Deployment 和 Service 配置示例，不能只写删除服务名。
- 新增服务必须完整复制官方 YAML，保留全部字段、容器、端口、探针和 `---` 分隔符；禁止缩写、省略号、“同上”或只给半段配置。
- 不同版本涉及不同服务时，必须按版本从低到高分别成块，非重复服务不得合并；每个版本块之间留一个空行，并在 YAML 注释中写明来源版本和服务名。
- 修改已有 Service 的指定位置必须单独成块，说明文件定位、字段路径、缩进和修改片段；不能与新增服务完整 YAML 混在一起。
- 任何“如果存在/若存在/如使用/按实际情况执行/同步修改”的条件操作，都必须给出对应完整命令或配置片段，不能只留下说明文字。提到 `run.sh`、`service.yaml` 或其他实际文件时，必须同时提供可执行的文件判断、定位和修改命令。
- 任何可执行事项不得只写“如存在则同步处理”或“按实际文件执行”。只要提到 `run.sh`，必须给出完整文件判断、`sed` 替换命令和 `fi` 结束符。
- 第二阶段分为 `#### 1. 滚动更新` 和 `#### 2. 非滚动更新`，分别保留内存条件、停止/更新命令和状态验证。
- fileInit 必须分别说明内置文件、S3 标准对象存储和外部对象存储的判断方式及命令；外部对象存储必须给预置包裸 URL。
- 离线导入必须使用 `gunzip -c xxx.tar.gz | ctr -n k8s.io image import -`，导入和验证命令前写明用途注释。

## 资源与 Markdown

- “提前准备”只列官方本次升级实际需要的资源。
- 下载表格使用 `| 文件 | 下载链接 |`，链接直接写完整 `https://`，不使用 Markdown 超链接或反引号。
- 目标 HAP 镜像导入前说明“导入 Docker/containerd 镜像仓库供升级使用”，验证命令前说明“确认目标镜像已成功导入”。
- 代码围栏必须是成对真实 ASCII 三反引号；不得出现 `\``。
- 版本信息表格紧跟主标题；普通说明不得写成一级标题。

## 交付前检查

使用 `tools/finalize_upgrade_doc.py`，不得直接调用转换器。它必须先运行 `tools/validate_upgrade_doc.py`，校验失败不得生成 HTML，也不得对用户声称交付完成。
