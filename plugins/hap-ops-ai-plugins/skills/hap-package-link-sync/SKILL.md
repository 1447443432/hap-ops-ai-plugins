# HAP 软件包信息同步

用于维护 HAP 私有部署软件包信息表。此 skill 只负责读取指定页面中的软件包表格、比对表记录并写入软件包元数据和地址，不负责文件传输或文件内容验证。

## 功能介绍

这个 skill 用来把 HAP 官方部署文档中的软件包信息同步到指定工作表，主要处理：

- 只读取指定页面中 `x86_64/AMD64` 和 `ARM64/AARCH64` 两个安装包下载表格中的软件包名称、版本、架构和完整地址；
- 读取目标表字段和现有记录；
- 判断记录是已存在、需要新增、需要更新地址，还是只需追加名称备注；
- 支持 amd64/x86_64 与 arm64/aarch64 分开处理；
- 生成带编号的变更清单，让用户选择具体操作范围；
- 仅在用户明确授权后，通过 `hap-cli` 执行新增或更新。

它不会下载或上传软件包，也不会在未确认时修改目标表。

## Windows UTF-8 输出约束

本 skill 在 Windows PowerShell 中执行时，必须先固定终端输入、输出和文件读取编码，避免中文字段名、清单和日志显示为乱码：

```powershell
[Console]::InputEncoding = [System.Text.UTF8Encoding]::new($false)
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
chcp 65001 > $null
```

- 读取 Markdown、YAML、JSON、技能文件时，必须显式指定 UTF-8，例如 `Get-Content -Encoding UTF8` 或 `[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)`。
- 写入文本时使用 UTF-8 无 BOM；不得使用未指定编码的 `>`、`>>`、`Out-File` 或 `Set-Content` 覆盖中文文件。
- `hap-cli --json` 的原始 JSON 必须按 UTF-8 解析后再提取字段；不要把终端乱码文本当作真实数据。
- 使用 PowerShell 抓取网页时，不得直接信任 `Invoke-WebRequest`.Content 的自动编码判断；官方页面响应必须从原始字节按 UTF-8 解码，再解析 HTML 表格。例如：

  ```powershell
  $response = Invoke-WebRequest -UseBasicParsing $url
  $html = [System.Text.Encoding]::UTF8.GetString($response.RawContentStream.ToArray())
  ```

- 若终端仍显示乱码，先停止比对和写入，改用 UTF-8 文件读取或结构化 JSON 解析；不得依据乱码内容生成变更清单。
- 输出给用户的清单使用真实中文和完整 URL；不要把调试命令输出原样当作结果。

## 默认简洁指令

由于本 skill 已固定官方文档和目标工作表，日常使用无需输入链接、应用 ID 或工作表 ID。以下任一指令都触发默认同步流程：

```text
同步软件包
更新软件包地址
同步部署包
```

默认使用：

- 官方文档：`https://docs-pdop.mingdao.com/deployment/cluster/architecture`
- 固定目标：本文件“固定目标”中的应用和工作表

只有在用户提供了其他文档链接、其他目标表或明确指定筛选范围时，才覆盖默认值。

## 操作说明

### 最简单的用法

日常使用直接输入简洁指令即可：

```text
同步软件包
```

需要指定其他文档时，再提供链接：

```text
同步这个文档：https://example.com/package-list
```

也可以按固定格式提供信息，格式见 [references/input-format.md](references/input-format.md)。

### 清单确认方式

skill 会先输出类似下面的清单：

```text
N1 新增：Docker / 29.9.3 / X86_64/AMD64
U1 更新 HAP 地址：mysql / 8.0.45 / ARM64/AARCH64
R1 追加备注：docker-(k8s 1.25)
```

默认情况下，回复以下内容表示全部执行：

```text
确认
```

如果只想处理部分项目，必须同时说明“指定项目怎么处理”和“剩余项目怎么处理”，例如：

```text
执行 N1、U1，其他跳过
```

```text
跳过 R1，其他执行
```

```text
只更新 Docker 的 ARM64 记录，其他不操作
```

如果只回复 `N1、U1`，但没有说明执行还是跳过，以及其他项目如何处理，skill 会先追问，不会写入。

执行前还会再次展示：

```text
本次将执行：N1、U1
本次跳过：R1
```

未选中的项目不会新增、更新或追加备注。

## 认证和敏感信息

- `hap auth login` 产生的认证缓存只允许保留在本机 hap-cli 配置目录，不得复制到项目目录、skill 目录或临时提交目录。
- 不读取、输出、硬编码、截图或记录 token、Cookie、Authorization、认证配置文件内容。
- `hap auth whoami` 只用于确认登录环境、组织和账号状态；输出给用户时隐藏邮箱和账号细节。
- Git 操作前检查 `git status --short`，确认没有 hap-cli 配置、token、日志、导出 JSON 或包含认证信息的临时文件。
- 推送前执行敏感信息检查；发现疑似凭据时立即停止提交和推送，并报告文件路径，不尝试自动上传或清理用户文件。

## 输入

支持官方文档链接或用户提供的结构化信息。缺少软件包身份、架构、版本或地址时，不猜测；先列出缺项并请求补充。

读取官方文档时：

- 提取表格中真实链接的 `href`，不能只复制页面显示文本。
- 来源范围严格限制为当前页面的两个架构表格：`各软件的 x86_64/AMD64 安装包下载链接` 和 `各软件的 ARM64/AARCH64 安装包下载链接`。
- 只解析这两个表格的当前 DOM/HTML 内容；不得点击、抓取或合并页面中的其他文档链接、导航页、组件页、历史版本页或外部下载页的额外条目。
- 按表格所属架构分组，每个架构生成独立输入项；架构必须来自表格分组，不得从其他页面或 URL 猜测。
- 架构例外：`Elasticsearch-ik` 和 `VictoriaLogs 数据源插件` 固定映射为目标表单选项 `通用`。这两个软件即使同时出现在 AMD64 和 ARM64 表格中，也必须先按软件包身份合并为一条逻辑输入，不能按两个架构新增两条记录。
- 架构例外清单以后只允许在用户明确补充并确认后扩展；未列入清单的软件仍严格使用页面所属架构。
- 保留完整 URL、文件名和查询参数，不因页面换行而截断。
- 同时记录文档中的软件包名称、版本和分组信息，用于判断软件包身份。

用户手工输入格式见 [references/input-format.md](references/input-format.md)。

## 必须遵循的流程

### 1. 先读取结构和现有记录

- 确认 `hap-cli` 已登录，并确认当前环境、组织和应用。
- 使用本机认证缓存完成登录检查，不要求用户把 token 粘贴到对话或项目文件中。
- 读取目标工作表字段，确认字段类型可写。
- 分页读取目标表的全部现有记录，不能只读取第一页；至少取得记录 ID、名称、版本、架构、HAP 地址、源地址和备注。
- 现有记录的架构是必填比对字段；如果接口返回空值、无法解析选项 key 或只剩下乱码，必须标记为数据异常并停止写入，不能仅凭 URL 文件名推断后新增或更新。
- 记录字段 ID 和原始值，后续更新只能针对明确的记录 ID。

如果 `hap-cli` 不可用、未登录、目标表字段无法确认或查询结果不完整，停止，不进行写入。

### 2. 识别软件包身份并规范化比对

- 架构：将 `x86_64`、`X86_64`、`amd64`、`AMD64` 视为同一架构；将 `aarch64`、`arm64`、`ARM64` 视为同一架构。
- 地址：只去除首尾空白，不改写协议、路径、查询参数或文件名。
- 版本：按原始字符串比较，不能从名称猜测版本。
- 软件包身份：用于区分不同软件，不等同于展示名称。名称中括号、平台或用途后缀（例如 `-(k8s 1.25)`）默认视为展示别名，不单独触发新增。
- 名称差异不能单独触发新增；先比较架构、版本和地址。只有架构或版本不同，或者文档明确表示是不同软件，才新增。
- URL 文件名只作辅助核对，不能单独推翻“架构、版本、地址一致”的结果。

候选匹配键为：`规范化软件包身份 + 规范化架构 + 版本`。

HAP 地址和源地址是候选记录的可变字段，不能放进候选匹配键。

### 3. 生成变更计划

- 架构、版本和 HAP 地址一致：不因名称不同而新增；如果名称不同且备注没有该名称，计划追加文档名称。
- 同一软件包身份、架构、版本一致，HAP 地址不同：只计划更新 HAP 地址，不新增。
- 架构或版本不同：新增一条完整记录；名称相似不能阻止新增。
- 文档明确表示是不同软件包：新增，即使架构、版本或地址碰巧相同。
- 源地址不同：只有用户明确要求同步源地址时才更新源地址；默认保持原值。
- 名称不同但已确认是同一软件包且身份、架构、版本一致：不新增；备注没有该名称时，计划追加 `文档名称：<新名称>`。
- 备注已有内容时只能追加，禁止覆盖、清空或重排原备注。
- 同软件包、同架构、同版本存在多条候选且无法唯一判断时，停止并列出候选记录，不自动修改。
- HAP 地址和源地址必须分别比较、分别展示、分别更新，不能用一个地址填充另一个字段。
- 用户只说“更新链接”时，默认指 HAP 地址；源地址是否更新必须单独列出并确认。

完整判定表见 [references/matching-rules.md](references/matching-rules.md)。

### 4. 必须先确认再写入

完成比对后，先输出带稳定编号的变更清单。编号使用 `N1`（新增）、`U1`（更新地址）、`R1`（追加备注）等形式，重新生成清单时重新编号。每项至少包含：操作类型、记录 ID、软件包身份、名称、版本、架构、原 HAP 地址、新 HAP 地址、原源地址、新源地址、原备注和追加内容；不变字段标注“保持不变”。

用户可以自由选择操作范围：

- `执行 N1、U2`
- `只更新 Docker 的 ARM64 记录`
- `新增 1 和 3，跳过其他`
- `执行版本 8.0.45 的两条，其他不操作`
- `不操作 U2，执行其余项目`

选择条件可以使用编号、名称、版本、架构、操作类型或记录 ID。若条件匹配多项，必须列出匹配项并请求用户明确选择，不能自行扩大范围。

默认策略是：用户明确回复“确认”“可以”“按清单执行”或“执行全部”时，执行全部清单。

如果用户单独指出一个或多个序号、名称、版本、架构或记录 ID，但没有同时说明指定项目和剩余项目如何处理，必须主动追问：

```text
已识别你指定的项目：N1、U1。
请补充：
1. 指定项目：执行 / 跳过？
2. 剩余项目：执行 / 跳过？
例如：执行 N1、U1，其他跳过。
```

只有范围和操作意图都明确后，才视为授权。用户补充信息、询问或修改条件不等于确认。

执行前再次输出“本次将执行”和“本次跳过”两组清单。未选中的项目保持不变，不得写入。

如果所有记录都一致且无备注需要追加，直接报告“无需新增或更新”，不要求确认。

### 5. 确认后的二次校验

用户确认后、任何写入前必须重新读取目标表字段和相关记录：

- 检查记录仍存在，字段 ID 未变化；
- 按同一匹配规则重新比较；
- 如果记录已被其他人修改，废弃旧清单并重新生成清单，不能覆盖新值；
- 只有二次校验结果与已确认清单一致时，才进入写入阶段。

### 6. 执行和汇总

- 新记录使用 `hap worksheet record create`，提交完整的必填字段。
- 地址或备注变更使用 `hap worksheet record update`，只提交实际发生变化的字段；不得把整行原始数据重新回写。
- 更新前再次核对记录 ID，禁止按名称盲改。
- 每次写入后保留返回的记录 ID 和结果。
- 任一写入失败，停止后续写入并报告已完成、未执行和失败项。
- 最终汇总新增、更新、追加备注、跳过和失败数量。
- 按用户选择的顺序执行；如果用户没有指定顺序，按清单编号从小到大执行。

## 禁止事项

- 不传输、不替换软件包文件。
- 不在用户确认前新增或更新记录。
- 不把名称差异直接当成新增条件。
- 不把不同架构或不同版本的记录合并。
- 不覆盖已有备注。
- 不根据截图、显示名称或 URL 路径猜字段 ID、记录 ID 或业务字段含义。
- 不把网页显示文本当作完整地址；地址缺失、截断或无法区分用途时停止。
- 变更清单中的地址使用完整原始 URL，不转换为 Markdown 超链接。
