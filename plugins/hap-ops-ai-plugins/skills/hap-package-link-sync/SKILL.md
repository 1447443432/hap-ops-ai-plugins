# HAP 软件包信息同步

用于维护 HAP 私有部署软件包信息表。此 skill 只负责读取指定页面中的软件包表格、比对表记录并写入软件包元数据、地址和文档使用状态，不负责文件传输或文件内容验证。

## 功能介绍

这个 skill 用来把 HAP 官方部署文档中的软件包信息同步到指定工作表，主要处理：

- 只读取指定页面中 `x86_64/AMD64` 和 `ARM64/AARCH64` 两个安装包下载表格中的软件包名称、版本、架构和完整地址；
- 读取目标表字段和现有记录；
- 判断记录是已存在、需要新增、需要更新地址，还是只需追加名称备注；
- 根据指定官方文档的当前两张架构表，核对已有记录并更新“文档使用状态”；
- 支持 amd64/x86_64 与 arm64/aarch64 分开处理；
- 生成带编号的变更清单，让用户选择具体操作范围；
- 仅在用户明确授权后，通过 `hap-cli` 执行新增或更新。

它不会下载或上传软件包，也不会在未确认时修改目标表。

## Windows UTF-8 输出约束

本 skill 在 Windows PowerShell 中执行时，必须先固定终端输入、输出和文件读取编码，避免中文字段名、清单和日志显示为乱码：

```powershell
[Console]::InputEncoding = [System.Text.UTF8Encoding]::new($false)
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
chcp 65001 > $null
```

- 读取 Markdown、YAML、JSON、技能文件时，必须显式指定 UTF-8，例如 `Get-Content -Encoding UTF8` 或 `[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)`。
- 写入文本时使用 UTF-8 无 BOM；不得使用未指定编码的 `>`、`>>`、`Out-File` 或 `Set-Content` 覆盖中文文件。
- `hap-cli --json` 的原始 JSON 必须按 UTF-8 解析后再提取字段；不要把终端乱码文本当作真实数据。
- 使用 PowerShell 抓取网页时，不得直接信任 `Invoke-WebRequest`.Content 的自动编码判断；官方页面响应必须从原始字节按 UTF-8 解码，再解析 HTML 表格。例如：

  ```powershell
  $response = Invoke-WebRequest -UseBasicParsing $url
  $html = [System.Text.Encoding]::UTF8.GetString($response.RawContentStream.ToArray())
  ```

- 若终端仍显示乱码，先停止比对和写入，改用 UTF-8 文件读取或结构化 JSON 解析；不得依据乱码内容生成变更清单。
- 输出给用户的清单使用真实中文和完整 URL；不要把调试命令输出原样当作结果。

## 默认简洁指令

由于本 skill 已固定官方文档和目标工作表，日常使用无需输入链接、应用 ID 或工作表 ID。以下任一指令都触发默认同步流程：

```text
同步软件包
更新软件包地址
同步部署包
```

默认使用：

- 官方文档：`https://docs-pdop.mingdao.com/deployment/cluster/architecture`
- 固定目标：本文件“固定目标”中的应用和工作表

只有在用户提供了其他文档链接、其他目标表或明确指定筛选范围时，才覆盖默认值。

## 操作说明

### 最简单的用法

日常使用直接输入简洁指令即可：

```text
同步软件包
```

需要指定其他文档时，再提供链接：

```text
同步这个文档：https://example.com/package-list
```

也可以按固定格式提供信息，格式见 [references/input-format.md](references/input-format.md)。

### 确认清单 HTML

每次从官方页面读取并完成比对后，必须先生成一个临时确认页，再等待用户确认；不得只在终端输出长清单，也不得直接写入目标表。确认页必须存放在项目的 `artifacts/tmp/hap-package-link-sync/` 下，且不得提交到 Git。

- 必须使用 [scripts/render_confirmation_html_v3.mjs](scripts/render_confirmation_html_v3.mjs) 生成，不手写静态 HTML 清单；该入口复用稳定模板，禁止使用临时简化渲染器覆盖正式模板。脚本只使用 Node.js 标准库。
- 默认只显示“新增”和“更新”两类可执行项；“无需新增或更新”必须保留在数据中，并通过动作筛选中的“无需操作”查看，不能从数据中删除。
- 页面必须支持：关键字搜索、重置搜索、架构筛选（全部、X86_64/AMD64、ARM64/AARCH64、通用）、动作筛选（全部、新增、更新、追加备注、无需操作、待判定）、分页和每页数量切换；不再显示“显示无需操作项”复选框，无需操作通过动作筛选查看。
- 页面中的统计项、筛选项和动作名称统一使用中文；保留稳定代码 `N`、`U`、`R`、`S`、`C` 供用户回复确认。确认说明要明确用户可以使用这些代码回复，例如 `执行 N1、U2，其他跳过`。
- 每条新增/更新/备注项必须展示完整操作数据：稳定编号、目标记录 ID（新增项标记“新记录”）、软件包名、规范化身份、版本、架构显示值、原 HAP 地址、新 HAP 地址、原源地址、新源地址、原备注、追加备注、拟执行字段和判定依据。单选项 key 仅用于内部写入和校验，不在确认页展示。URL 必须是完整纯文本，不得只显示文件名或超链接文字。
- 页面顶部必须显示来源页面、读取范围、原始表格行数、去重后逻辑条数、严格命中数、官网待判定数、目标表记录数、完全匹配数、新增数、更新数、备注数、无需操作数和待判定数。原始行数、逻辑条数、严格命中数、官网待判定数和可执行条数必须分开统计。
- HTML 只是确认载体，不代表已授权；只有用户明确确认后，才进行二次读取和写入。

确认页的筛选、分页只改变展示，不改变计划数据；在用户确认前必须以原始计划 JSON 为准重新核对，不能根据页面当前筛选结果误删未显示项。渲染脚本的输入必须是脱敏计划数据，不得包含 token、Cookie、Authorization 或 hap-cli 配置。

### 清单确认方式

skill 会先输出类似下面的清单：

```text
N1 新增：Docker / 29.9.3 / X86_64/AMD64
U1 更新 HAP 地址：mysql / 8.0.45 / ARM64/AARCH64
R1 追加备注：docker-(k8s 1.25)
```

默认情况下，回复以下内容表示全部执行：

```text
确认
```

如果只想处理部分项目，必须同时说明“指定项目怎么处理”和“剩余项目怎么处理”，例如：

```text
执行 N1、U1，其他跳过
```

```text
跳过 R1，其他执行
```

```text
只更新 Docker 的 ARM64 记录，其他不操作
```

如果只回复 `N1、U1`，但没有说明执行还是跳过，以及其他项目如何处理，skill 会先追问，不会写入。

执行前还会再次展示：

```text
本次将执行：N1、U1
本次跳过：R1
```

未选中的项目不会新增、更新或追加备注。

## 认证和敏感信息

- `hap auth login` 产生的认证缓存只允许保留在本机 hap-cli 配置目录，不得复制到项目目录、skill 目录或临时提交目录。
- 不读取、输出、硬编码、截图或记录 token、Cookie、Authorization、认证配置文件内容。
- `hap auth whoami` 只用于确认登录环境、组织和账号状态；输出给用户时隐藏邮箱和账号细节。
- Git 操作前检查 `git status --short`，确认没有 hap-cli 配置、token、日志、导出 JSON 或包含认证信息的临时文件。
- 推送前执行敏感信息检查；发现疑似凭据时立即停止提交和推送，并报告文件路径，不尝试自动上传或清理用户文件。

## 输入

支持官方文档链接或用户提供的结构化信息。缺少软件包身份、架构、版本或地址时，不猜测；先列出缺项并请求补充。

读取官方文档时：

- 提取表格中真实链接的 `href`，不能只复制页面显示文本。
- 来源范围严格限制为当前页面的两个架构表格：`各软件的 x86_64/AMD64 安装包下载链接` 和 `各软件的 ARM64/AARCH64 安装包下载链接`。
- 只解析这两个表格的当前 DOM/HTML 内容；不得点击、抓取或合并页面中的其他文档链接、导航页、组件页、历史版本页或外部下载页的额外条目。
- 按表格所属架构分组，每个架构生成独立输入项；架构必须来自表格分组，不得从其他页面或 URL 猜测。
- 架构例外：`Elasticsearch-ik` 和 `VictoriaLogs 数据源插件` 固定映射为目标表单选项 `通用`。这两个软件即使同时出现在 AMD64 和 ARM64 表格中，也必须先按软件包身份合并为一条逻辑输入，不能按两个架构新增两条记录。
- 架构例外清单以后只允许在用户明确补充并确认后扩展；未列入清单的软件仍严格使用页面所属架构。
- 本次页面同步只允许纳入当前页面两张架构表中实际出现的行；不得因为名称相似、URL 路径相似或页面中存在其他下载入口而补抓其他页面内容。原始行数、去重规则和每一条被排除的行都必须可追溯。
- `MongoDB` 与 `MongoDB Tools` 必须分别作为不同的软件身份处理。必须依据页面当前表格实际给出的包名、版本、架构和完整地址逐条判定；外部说明页、跳转页或只有“MongoDB”字样但没有具体版本/架构/包地址时，标记“待判定”，不得用文件名或历史记录猜测。MongoDB 数据库包不能与 MongoDB Tools 合并，也不能因为名称相近而覆盖已有记录。
- 详细的来源范围、动作分类、单选架构和 MongoDB 判定规则见 [references/source-scope-and-matching.md](references/source-scope-and-matching.md)，需要处理这些边界时必须先读取该参考文件。
- 保留完整 URL、文件名和查询参数，不因页面换行而截断。
- 同时记录文档中的软件包名称、版本和分组信息，用于判断软件包身份。

用户手工输入格式见 [references/input-format.md](references/input-format.md)。

## 必须遵循的流程

### 0. 本轮运行的性能和认证约束

- 每次同步任务开始时只执行一次 `hap auth whoami` 作为登录检查；检查成功后，本轮任务复用现有本地认证缓存，禁止重复执行 `hap auth login`、重复 reauth 或反复确认账号。
- 只有 `whoami` 明确返回未登录、认证过期或权限错误时，才暂停读取并提示重新认证；认证失败后也不得循环重试。
- 不在正常同步流程中调用 `hap --help`、`worksheet --help` 或其他帮助命令；命令格式以本 skill 和 `hap-cli` skill 为准。
- 字段结构只读取一次；目标记录按最大允许页大小分页读取一次，解析后保存在本轮内存结果中，后续比对、清单生成和二次校验分别使用已读取结果，禁止无目的重复全表扫描。
- 单选字段优先使用结构化 JSON；若 CLI JSON 未展开单选值，改用一次 `--response-format md` 读取对应字段，不得同时反复调用两种格式。
- 不输出完整原始 JSON、完整 CLI 帮助或调试转储；只提取字段、记录 ID、必要地址和变更摘要，避免终端乱码与上下文膨胀。
- 单次只读命令超过 60 秒没有结果时，停止该命令并报告阶段，不重复启动同一命令；不得让多个相同的长任务并行运行。
- 读取阶段完成后立即向用户报告“认证、字段、记录、官方页面”四项状态，再生成清单；不要在用户不可见的长时间循环中继续抓取。

### 1. 先读取结构和现有记录

写入幂等约束：每一条新增写入前，必须重新按身份、版本、架构 key 和 HAP 地址核对当前目标表；若已存在完全匹配记录，立即跳过，不得创建。每一条备注追加前，必须重新读取目标备注；若已包含待追加内容，立即跳过，不得重复追加。写入命令超时、网络错误、格式错误或结果不明确时，禁止直接重试，必须先复核实际状态后再决定跳过、补写或报告失败。确认清单只能作为候选，实时复核结果优先。

- 确认 `hap-cli` 已登录，并确认当前环境、组织和应用。
- 使用本机认证缓存完成登录检查，不要求用户把 token 粘贴到对话或项目文件中。
- 读取目标工作表字段，确认字段类型可写。
- 分页读取目标表的全部现有记录，不能只读取第一页；至少取得记录 ID、名称、版本、架构、HAP 地址、源地址和备注。
- 现有记录的架构是必填比对字段；如果接口返回空值、无法解析选项 key 或只剩下乱码，必须标记为数据异常并停止写入，不能仅凭 URL 文件名推断后新增或更新。
- 对单选字段，若 `hap-cli --json` 的记录接口没有直接展开显示文本，必须使用 `--response-format md` 或等价的结构化字段值读取选项 key；不能把“JSON 中未展开”误判成“字段为空”。只有确认真实值为空或无法解析时，才按数据异常停止。
- 记录字段 ID 和原始值，后续更新只能针对明确的记录 ID。

如果 `hap-cli` 不可用、未登录、目标表字段无法确认或查询结果不完整，停止，不进行写入。

### 2. 识别软件包身份并规范化比对

- 架构：将 `x86_64`、`X86_64`、`amd64`、`AMD64` 视为同一架构；将 `aarch64`、`arm64`、`ARM64` 视为同一架构。
- 地址：只去除首尾空白，不改写协议、路径、查询参数或文件名。
- HAP 下载地址写入白名单：只有完整 URL 的主机名严格为 `pdpublic.mingdao.com` 或 `pdpublic.nocoly.com` 时，才允许写入目标表的“HAP 地址”字段。协议必须为 `https`；其他域名（包括官网产品页、下载入口页、GitHub、MongoDB 官方站、镜像站和任意跳转页）不得写入 HAP 地址，只能作为“源地址”或判定依据保留。
- 入口页特殊处理：如果官方文档只提供官网入口页而没有 `pdpublic.mingdao.com`/`pdpublic.nocoly.com` 的具体 HAP 包地址，必须标记“待判定/仅供参考”，不得把入口页 URL 当作 HAP 地址，不得据此执行 `U` 更新或 `N` 新增。即使 AMD64 与 ARM64 共用同一个官网入口，也只能说明来源入口共用，不能突破 HAP 地址白名单。
- 版本：按原始字符串比较，不能从名称猜测版本。
- 版本提取优先使用来源表中完整软件包 URL 里明确且唯一的版本号；只有软件包名称本身明确标注版本、且 URL 没有冲突时才使用名称版本。URL 和名称都无法唯一确定版本时必须标记待判定，不得用历史记录补猜。
- 版本号需要区分“发布版本”和“构建标识”：例如 Grafana URL `/release/13.1.1/grafana_13.1.1_29761037902_linux_*.tar.gz` 的业务版本是 `13.1.1`，`29761037902` 仅为构建标识，不得拼入版本字段。目标表名称为“监控-Grafana”或等价监控别名时，与官方名称“Grafana”按同一软件身份比对，但仍必须核对架构、发布版本和 HAP 地址。
- 特殊版本解析仅对本页面明确列出的软件生效，不得推广到其他软件：
  - `Docker Compose`、`Promtail`、`K8S Metrics 服务镜像`、`Milvus`：如果完整软件包 URL 和软件包名称都没有明确版本，版本字段使用占位值 `latest`，不再标记为待判定；如果 URL 已明确给出版本，仍以 URL 版本为准。
  - `CentOS`：文件名 `centos7.9.2009.tar.gz` 中的 `7.9.2009` 是版本。
  - `MinIO`：文件名中的 `RELEASE.2025-04-22T22-12-26Z` 这类完整 `RELEASE.<时间戳>` 是版本，必须原样保留。
  - `mingdaoyun-command`：文件名中的 `node1018-python36` 是版本，必须原样保留。
  - 以上规则是官方软件包命名约定，不是根据历史记录、名称相似或模糊推测版本；若文件名与名称冲突，必须标记待判定。
- 软件包身份：用于区分不同软件，不等同于展示名称。名称中括号、平台或用途后缀（例如 `-(k8s 1.25)`）默认视为展示别名，不单独触发新增。
- 名称差异不能单独触发新增；先比较架构、版本和地址。只有架构或版本不同，或者文档明确表示是不同软件，才新增。
- URL 文件名只作辅助核对，不能单独推翻“架构、版本、地址一致”的结果。

候选匹配键为：`规范化软件包身份 + 规范化架构 + 版本`。

HAP 地址和源地址是候选记录的可变字段，不能放进候选匹配键。

### 3. 生成变更计划

- 架构、版本和 HAP 地址一致：不因名称不同而新增；如果名称不同且备注没有该名称，计划追加文档名称。
- 同一软件包身份、架构、版本一致，HAP 地址不同：只计划更新 HAP 地址，不新增。
- 架构或版本不同：新增一条完整记录；名称相似不能阻止新增。
- 文档明确表示是不同软件包：新增，即使架构、版本或地址碰巧相同。
- 源地址不同：只有用户明确要求同步源地址时才更新源地址；默认保持原值。
- 名称不同但已确认是同一软件包且身份、架构、版本一致：不新增；备注没有该名称时，计划追加 `文档名称：<新名称>`。
- 备注已有内容时只能追加，禁止覆盖、清空或重排原备注。
- 同软件包、同架构、同版本存在多条候选且无法唯一判断时，停止并列出候选记录，不自动修改。
- 不能仅凭“完整 URL 不同”判定新增；必须先核对软件身份、版本和架构：三者一致且 HAP 地址不同才是 `U` 更新，任一身份/版本/架构不同才是 `N` 新增，三者和地址都一致才是 `S` 跳过。
- 版本无法从文档明确取得、软件身份存在别名冲突或同名记录无法唯一匹配时，标记为“待判定”并暂停该项；不得使用临时的 `C` 编号代替 `N/U/S`，也不得在未判定时请求执行。
- HAP 地址和源地址必须分别比较、分别展示、分别更新，不能用一个地址填充另一个字段。
- 用户只说“更新链接”时，默认指 HAP 地址；源地址是否更新必须单独列出并确认。
- 用户要求同步“文档使用状态”时，建立当前页面软件包集合：严格取两张架构表的完整 HAP 地址，按架构映射后与目标记录的 HAP 地址和架构精确比较。精确匹配为“在用”，不匹配为“未使用”；名称、备注、旧版本或其他页面内容不能单独改变判断。官网只有下载入口页、没有具体包地址的项目（例如 MongoDB/Mongo Tools 当前入口页）计入“官网待判定”，不计入严格命中，也不得据此把目标记录标为“在用”。
- 文档使用状态同步只更新该单选字段，不连带修改名称、版本、架构、HAP 地址、源地址、备注或状态字段；字段已有相同选项时标记为无需操作。

#### 严格的全量核对和动作分类

- 计划必须覆盖当前页面两张表的每一条原始行；同一逻辑软件只有在规则明确允许时才能去重。每一条原始行要保留 `sourceRowId`、原始名称、原始版本、原始架构组和完整 HAP 地址，便于追溯“为什么合并/排除”。
- 动作只能是 `N`（新增）、`U`（更新 HAP 地址）、`R`（仅追加备注）、`S`（完全匹配、无需操作）或“待判定”。禁止先把不匹配项统称为待处理，再凭名称批量新增。
- `U` 必须证明软件身份、规范化架构和版本与唯一目标记录一致，且只有 HAP 地址不同；源地址变化必须单独列为另一项或明确保持不变。
- `N` 必须给出完整的新记录字段，不能只给名称和链接。`U/R` 必须给出记录 ID、原值、新值和实际写入字段。
- 目标表中的架构是单选字段：写入时使用实时字段结构返回的 option key，展示时同时显示“名称 + key”；不得写入自由文本或猜测 key。通用软件只能写入实时返回的“通用” option key。
- MongoDB 和 MongoDB Tools 的平台包、版本和架构必须分别映射到目标表中的具体候选记录。只要无法唯一证明对应关系，就进入待判定，不得自动新增、更新或合并。

完整判定表见 [references/matching-rules.md](references/matching-rules.md)。

### 4. 必须先确认再写入

完成比对后，先输出带稳定编号的变更清单。清单必须按架构分组，顺序固定为：`X86_64/AMD64`、`ARM64/AARCH64`、`通用`。每个架构组内逐条列出软件包名称、版本、完整地址、当前状态和拟执行动作；不得只输出“发现 N 条差异”的数量摘要。

同时生成确认 HTML。终端只输出 HTML 的绝对路径、统计摘要和简短使用说明；详细数据以 HTML 为准。默认筛选“新增、更新”，但页面数据必须包含全部 `N/U/R/S/待判定` 项。

清单格式至少遵循下面的结构：

```text
【X86_64/AMD64】
1. Docker
   • 版本：29.9.3
   • 地址：https://...
   • 当前状态：目标表不存在 / 已存在但地址不同 / 已完全匹配
   • 拟执行：新增 / 仅更新 HAP 地址 / 跳过

【ARM64/AARCH64】
1. Docker
   • 版本：29.9.3
   • 地址：https://...
   • 当前状态：目标表不存在
   • 拟执行：新增

【通用】
1. Elasticsearch-ik
   • 版本：9.5.6
   • 地址：https://...
   • 当前状态：目标表不存在
   • 拟执行：新增
```

清单中的每一项都必须带稳定编号，不能只给待处理项编号：`N1`（新增）、`U1`（更新地址）、`R1`（追加备注）、`S1`（完全匹配、跳过）。无法判定的项目使用单独的“待判定”区，不进入确认执行清单。编号按架构分组顺序从上到下生成；重新生成清单时重新编号。需要更新的项目至少包含：记录 ID、原 HAP 地址、新 HAP 地址、原源地址、新源地址、原备注和追加内容；不变字段标注“保持不变”。已完全匹配的项目也必须列出并标记“跳过”，不能从清单中隐去。

用户可以自由选择操作范围：

- `执行 N1、U2`
- `只更新 Docker 的 ARM64 记录`
- `新增 1 和 3，跳过其他`
- `执行版本 8.0.45 的两条，其他不操作`
- `不操作 U2，执行其余项目`

选择条件可以使用编号、名称、版本、架构、操作类型或记录 ID。若条件匹配多项，必须列出匹配项并请求用户明确选择，不能自行扩大范围。

默认策略是：用户明确回复“确认”“可以”“按清单执行”或“执行全部”时，执行全部清单。

如果用户单独指出一个或多个序号、名称、版本、架构或记录 ID，但没有同时说明指定项目和剩余项目如何处理，必须主动追问：

```text
已识别你指定的项目：N1、U1。
请补充：
1. 指定项目：执行 / 跳过？
2. 剩余项目：执行 / 跳过？
例如：执行 N1、U1，其他跳过。
```

只有范围和操作意图都明确后，才视为授权。用户补充信息、询问或修改条件不等于确认。

执行前再次输出“本次将执行”和“本次跳过”两组清单。未选中的项目保持不变，不得写入。

如果所有记录都一致且无备注需要追加，直接报告“无需新增或更新”，不要求确认。

### 5. 确认后的二次校验

用户确认后、任何写入前必须重新读取目标表字段和相关记录：

- 检查记录仍存在，字段 ID 未变化；
- 按同一匹配规则重新比较；
- 如果记录已被其他人修改，废弃旧清单并重新生成清单，不能覆盖新值；
- 只有二次校验结果与已确认清单一致时，才进入写入阶段。

二次校验必须包含幂等检查：

- `N` 新增：按身份、版本、架构单选项 `key`、HAP 地址重新查当前表；发现完全匹配记录时改判为 `S`，跳过创建。
- `U` 更新地址：重新读取目标 `rowId`，只有当前 HAP 地址仍等于清单中的原值时才更新；否则停止并重新生成清单。
- `R` 追加备注：重新读取目标备注；若已包含待追加的完整标记文本，则改判为 `S`，跳过追加；否则保留原 RichText 内容后追加。
- 执行中断、超时、网络错误、命令格式错误或返回结果不明确时，禁止直接重试；先重新读取并按以上规则确认实际状态。重试只允许处理“复核后仍明确需要操作”的项目。
- 批量执行不得把旧清单直接当作创建队列；每条写入都必须经过实时复核，并记录 `成功 / 已存在跳过 / 已更新跳过 / 失败` 状态。

#### 防重复和可恢复执行约束

- 写入计划必须先按 `rowId` 去重；同一个 `rowId` 在本轮执行集合中只能出现一次。新增项必须按“规范化身份 + 架构 option key + 版本 + HAP 地址”去重，不能按展示名称或清单编号去重。
- 不允许并行写入同一目标表，也不允许启动可能超过终端超时上限的长批次。默认串行执行，每批最多 2～3 条；批次大小只能影响调度，不能改变计划内容。
- 执行前创建本轮专用检查点文件，至少记录：计划指纹、目标表 ID、字段 ID、rowId、拟写入 option key、状态（待执行/成功/已跳过/失败）和时间。每条记录完成复核或写入后立即追加并安全保存检查点，不能等整批结束才落盘。
- 任何命令超时、终端中断、结果为空或结果无法确认时，立即停止后续写入；不得按原批次重新执行。恢复时先重新读取全表，按 rowId 和当前字段值重建待执行集合：目标值已存在就标记“已跳过”，只有仍明确缺少目标值的记录才允许继续。
- 重新执行或恢复执行时，必须排除检查点中“成功”和“已跳过”的 rowId，并再次校验当前记录仍属于本轮计划；禁止按序号范围、分页位置或旧 HTML 页面直接重放。
- 发现同一个 rowId 对应的名称、架构、版本、HAP 地址或其他关键字段已变化，立即暂停该记录并重新生成清单；不得覆盖新值。发现目标表出现新的完全匹配记录时，新增动作改判为“已存在跳过”。
- 最终验收必须重新读取目标表全部记录，检查：rowId 无重复处理、拟写入字段值全部正确、未设置目标值为 0、官方严格命中数与“在用”数一致、官网待判定项未被误标为“在用”，并输出失败和跳过明细。

### 6. 执行和汇总

- 认证只检查一次并复用本地缓存：

  ```powershell
  hap --profile <profile> --json auth whoami
  ```

  若当前终端没有 `hap` 可执行文件，但已安装 `hap-cli`，使用等价入口 `uvx --from hap-cli hap`；不要因为命令发现失败而重复登录。需要临时指定缓存目录时使用任务专用目录，例如 `$env:TEMP\hap-cli-cache`，不得把缓存、token、Cookie 或日志写入仓库。

- 先设置默认应用；记录新增、更新、删除命令不接受 `--app-id`，必须依赖默认应用：

  ```powershell
  hap --profile <profile> app select <APP_ID>
  ```

- 读取字段和记录使用全局 `--json`，且必须放在 `hap` 后、子命令前；记录查询必须分页到 `total`：

  ```powershell
  hap --profile <profile> --json worksheet fields <WORKSHEET_ID> -a <APP_ID>
  hap --profile <profile> --json worksheet record list <WORKSHEET_ID> -n 100 -p 1 --include-total-count
  hap --profile <profile> --json worksheet record list <WORKSHEET_ID> -n 100 -p 2 --include-total-count
  ```

- 新记录使用 `hap worksheet record create`，提交名称、版本、实时架构 option `key`、HAP 地址和必填的“地址是否有效” option `key`。不要把架构显示文本直接写入单选字段：

  ```powershell
  hap --profile <profile> --json worksheet record create <WORKSHEET_ID> `
    -f '<NAME_FIELD>=Docker' `
    -f '<VERSION_FIELD>=29.9.3' `
    -f '<ARCH_FIELD>=<LIVE_ARCH_OPTION_KEY>' `
    -f '<HAP_URL_FIELD>=https://...' `
    -f '<VALID_FIELD>=<LIVE_VALID_OPTION_KEY>'
  ```

- 地址或备注变更使用正确的两个位置参数 `WORKSHEET_ID ROW_ID`，只提交实际变化字段；不得按名称盲改，也不得把整行重新回写：

  ```powershell
  hap --profile <profile> --json worksheet record update <WORKSHEET_ID> <ROW_ID> -f '<HAP_URL_FIELD>=https://...'
  hap --profile <profile> --json worksheet record update <WORKSHEET_ID> <ROW_ID> -f '<REMARK_FIELD>=<原 RichText 内容 + 追加内容>'
  ```

- 备注字段是 RichText；追加前必须保留原 HTML/富文本，不得用空值或纯文本覆盖原内容。
- 每条写入成功后立即记录返回的 `rowId` 和检查点；未明确确认成功前不重复调用同一写入命令。
- 任一项目写入失败，默认停止后续写入；只有完成只读幂等复核并确认仍需操作后，才允许继续或重试。
- 每次写入后保留返回的记录 ID 和结果。
- 最终汇总新增、更新、追加备注、跳过和失败数量。
- 按用户选择的顺序执行；如果用户没有指定顺序，按清单编号从小到大执行。

## 禁止事项

- 不传输、不替换软件包文件。
- 不在用户确认前新增或更新记录。
- 不把名称差异直接当成新增条件。
- 不把不同架构或不同版本的记录合并。
- 不覆盖已有备注。
- 不根据截图、显示名称或 URL 路径猜字段 ID、记录 ID 或业务字段含义。
- 不把网页显示文本当作完整地址；地址缺失、截断或无法区分用途时停止。
- 变更清单中的地址使用完整原始 URL，不转换为 Markdown 超链接。
