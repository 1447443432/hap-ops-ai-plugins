# 场景 A / 场景 B 差异说明（核心参考）

> 本文件基于对两份真实部署文档（场景A_未开启Swarm、场景B_开启Swarm）逐行 diff 提炼。
> 生成任何文档时，A/B 的差异**只**体现在下列条目；其余内容两场景完全一致。
> **重要**：输出文档的正文与文件名都不出现“场景A/场景B/Scenario A/B”字样（见 constraints.md 命名规范）。
> A/B 仅作为生成时的内部分支开关，本文件用于向用户解释 A/B 区别、以及驱动生成逻辑。

---

## 一句话区别

- **场景 A**：File / MinIO 所在 4 台中间件节点之间 **VXLAN 未开启**（Swarm 端口 2377、overlay 4789 不通）。因此 4 个节点各自独立运行一个“单节点 Docker Swarm”，互不编排。
- **场景 B**：File / MinIO 所在 4 台节点之间 **VXLAN 正常开启**（2377、4789 互通）。4 个节点组成 **同一个 Docker Swarm 集群**，由 Node01 作为 manager 统一编排调度。

判断依据：客户网络环境中，中间件 4 节点（默认 192.168.1.51/52/53/54）之间 TCP 2377、UDP 4789 是否互通。通则用 B，不通则用 A。

---

## 差异点逐条（生成时据此分支）

差异**全部集中在部署文档的 5.3（MinIO 部署）与 5.4（File 服务部署）两章**，以及由此连带的端口规划、架构图、运维文档组件表。其余章节（系统初始化、MongoDB、MySQL MGR、Redis、Kafka、ES、K8s、Istio、微服务、Flink、Nginx、监控）A/B 完全相同。

### 1. MinIO 对外端口（A/B 统一，不再区分）

| 项 | 场景 A | 场景 B |
|---|---|---|
| MinIO API 端口 | 4 节点**各自 9011 / 9012 / 9013 / 9014** | 同左（4 节点**各自 9011 / 9012 / 9013 / 9014**） |
| 容器内端口 | 统一 9000（宿主端口区分） | 统一 9000（宿主端口区分） |
| 端口规划表述 | `MinIO 对象存储 API（4 节点 IP 各对应 9011/9012/9013/9014）` | 同左 |

> **设计决策**：MinIO 端口在 A/B 一律 9011-9014，使两场景的网络策略（防火墙端口开放）完全一致，无需按场景区分。
> 这与旧素材不同——旧的场景 A 用 9000:9000；新标准下场景 A 也用 9011:9000、9012:9000、9013:9000、9014:9000（宿主 901X、容器内仍 9000）。
> 注意：场景 A 是 4 个独立单节点 Swarm，各节点只跑自己的 minio 服务，端口虽各异但因分处不同物理机不冲突。

### 2. Swarm 管理端口 2377（仅 B 开放）

- 场景 B 端口规划表**额外增加一行**：
  `MinIO + File 共置节点 01-04 | 2377 | TCP | Swarm 4 节点之间互通 | Docker Swarm 集群管理通信`
- 场景 A **不开 2377**：A 是 4 个相互独立的单节点 Swarm，不 join、不互相编排，无需集群管理端口。
- **这（2377 + overlay 4789 是否互通）才是 A/B 唯一的真实网络差异。**

### 3. Swarm 初始化方式（5.3.1）

- **场景 A**：4 个节点各自执行 `docker swarm init`，形成 4 个相互独立的单节点 Swarm；**无需 join、无需记录 node ID**。
- **场景 B**：仅 Node01 执行 `docker swarm init --advertise-addr 192.168.1.51`；Node02/03/04 执行 `docker swarm join --token xxx` 加入；随后 `docker node ls` 记录各节点 ID（后续 yaml 的 placement 要用）。

### 4. minio.yaml 结构（5.3.3）

- **场景 A**：每个节点一份**只含本节点单个服务**的 minio.yaml（Node01 只定义 minio1，Node02 只定义 minio2…）。各节点宿主端口按 9011/9012/9013/9014、容器内 9000（即 `9011:9000`…）。**无 `deploy.placement`**。
- **场景 B**：4 个节点放**同一份完整 minio.yaml**（含 minio1~minio4 四个服务），每个服务通过 `deploy.placement.constraints.node.id == <对应节点ID>` 绑定物理节点；端口同样分别 `9011:9000`、`9012:9000`、`9013:9000`、`9014:9000`。
- **A/B 端口一致，差异只在：A 是每节点一份单服务无 placement；B 是一份完整配置带 placement。**

### 5. file.yaml 结构（5.4.2）

- **场景 A**：每个节点一份**只含本节点单个 file 服务**的 file.yaml（fileN），端口按节点 9001/9002/9003/9004（容器内统一 9000）。无 placement。
- **场景 B**：4 个节点放**同一份完整 file.yaml**（含 file1~file4），各服务用 `deploy.placement.constraints.node.id` 绑定；端口 9001~9004。复用 5.3 查到的 node.id。

### 6. 启停脚本与执行（5.3 / 5.4 末尾）

- **场景 A**：4 个节点**分别**创建启停脚本、**分别**执行启动与检查（每节点都做）。
- **场景 B**：**仅 Node01** 创建启停脚本并执行；Swarm 自动调度到 4 个节点。

### 7. s3-config.json 的 bucketEndPoint（5.4.1，A/B 统一）

- **A/B 一致**：4 节点分别按 IP→端口映射填写：.51→9011、.52→9012、.53→9013、.54→9014（如 `http://192.168.1.51:9011`）。
- File 对接说明：A/B 都填任一节点的 901X 端口（如 9011，也可 9012/9013/9014）。
- MinIO 通常通过 IP 访问，须保留 `"addressingModel": 1`；对接云厂商 OSS/COS/S3 时删除该参数。

### 8. Flink flink-conf.yaml 的 s3.endpoint（约第七章 Flink，A/B 统一）

- **A/B 一致**：`s3.endpoint: 192.168.1.51:9011`，注释“可指向任一 MinIO 节点的对应端口（9011/9012/9013/9014 任选其一）”。

### 9. 运维文档组件表（连带差异）

- 中间件节点 MinIO+File 行的端口列：A/B **都是** `901X / 900X`（MinIO 901X、File 900X）。
- 安装路径/数据目录两场景一致（`/usr/local/minio`、`/data/minio + /data/file`）。

### 10. 架构图（连带差异）

- 场景 A 架构图中间件层标注：`各节点独立运行`、`MinIO 4 节点 9011-9014`、`单节点 docker swarm（不互通 2377/4789）`。
- 场景 B 架构图中间件层标注：`Docker Swarm 集群统一编排`、`MinIO 4 节点 9011-9014`、`Swarm overlay 2377/4789 互通`。
- 两者 MinIO 端口标注相同（9011-9014）；区别在“独立 vs 集群编排”与“2377/4789 是否互通”。

## 不随 A/B 变化的内容（务必保持一致，避免误改）

> 易错点 2：A/B 端口与网络策略已完全统一，**唯一真实差异是是否组 Swarm 集群**（连带 2377 是否开、yaml 是否带 placement、启停脚本是否仅 Node01 执行）。生成时不要再因场景去改任何端口。
